STEP 1 — RECOVER THE BLEND (the model does not state it, so I solved for it).
Effective input multiplier at h=0.85, pricing the 15% miss at base: 0.85(0.1) + 0.15(1.0) = 0.235.
All-Opus input: 47.5 x 5 x 0.235 = $55.81. All-Sonnet-intro: 47.5 x 2 x 0.235 = $22.33.
Solve x(55.81) + (1-x)(22.33) = 31.72 → 33.48x = 9.39 → x = 0.280. So 28.0% of INPUT tokens on Opus.
All-Opus output: 2.5 x 25 = $62.50. All-Sonnet: 2.5 x 10 = $25.00.
Solve y(62.50) + (1-y)(25.00) = 33.25 → 37.5y = 8.25 → y = 0.220. So 22.0% of OUTPUT tokens on Opus.
Two independently derived splits both land near one quarter of traffic on the orchestrator. THE MODEL IS INTERNALLY COHERENT and reproduces to the cent: 31.72 + 33.25 = $64.97.

STEP 2 — THE HEADLINE CLAIM: CONFIRMED.
Output share of VOLUME = 2.5 / 50.0 = 5.00%.
Output share of BILL = 33.25 / 64.97 = 51.18%.
Effective rates: input $31.72/47.5 = $0.668/MTok; output $33.25/2.5 = $13.30/MTok. Observed ratio 19.9x.
Structural single-model ratio: 5 / 0.235 = 21.28x — IDENTICAL for Opus 5, Sonnet 5 intro and Sonnet 5 post-September, because all three price output at exactly 5x input and cache-read at exactly 0.1x. Observed 19.9 sits just below structural 21.3 because Opus carries a larger share of input (28%) than of output (22%).

STEP 3 — THE FRAMING NEEDS ONE CORRECTION, AND IT IS THE PART THAT DETERMINES WHERE TO AIM.
The owner attributes output's half-share to "output is priced 5x higher AND cannot be cached." Both true, but the weights are wildly unequal and the second dominates:
- Volume ratio is 19:1 input:output.
- At 5x list price with NO caching, output would be 5/(5+19) = 20.8% of the bill.
- 85% caching divides the effective input price by 4.26 (= 1/0.235), taking the per-token ratio to 21.3x → output share = 21.3/(21.3+19) = 52.9% single-model, 51.2% at the owner's blend.
THE 5x MULTIPLE GETS YOU TO ~21%. CACHING CARRIES IT FROM 21% TO 51%. Output's share of the bill is therefore a FUNCTION OF CACHE SUCCESS, not a fixed property of the workload — which is why cache work and output work are complements, and why every point of cache improvement raises the dollar value of every output-token intervention.

STEP 4 — DEFECT FOUND IN THE STATED CACHE-SENSITIVITY CURVE.
Implied blended base input rate B = 31.72 / (47.5 x 0.235) = $2.842/MTok.
Input cost I(h) = 47.5 x 2.842 x (1 - 0.9h) = 135.0 x (1 - 0.9h).
- h = 0.85: 135.0 x 0.235 = $31.72 → total $64.97. Stated $65. ✓
- h = 0.50: 135.0 x 0.550 = $74.25 → total $107.50. Stated $108. ✓
- h = 0.00: 135.0 x 1.000 = $135.00 → total $168.25. Stated $155. ✗ UNDERSTATED BY ~$13 (8%).
The 0%-caching anchor is wrong; the true 0%→85% spread is $103, not $90. This strengthens rather than weakens the caching case.
MARGINAL VALUE: dI/dh = -135.0 x 0.9 = -$121.50 per unit h, i.e. $1.215 PER PERCENTAGE POINT of hit rate. Hence 50→85% = $42.53; 85→92% = $8.51; 85→95% = $12.15. (W4a's "~$1.2/pp" and W4e's "$12.15" are both correct.)

STEP 5 — THE CACHE-WRITE CORRECTION: RIGHT ARITHMETIC, BUT ARCHITECTURE-DEPENDENT, NOT AN ERROR.
W4e notes the model prices the 15% non-read slice at 1.0x when a 5-minute cache write actually bills at 1.25x. If the ENTIRE non-read slice is writes: multiplier = 0.85(0.1) + 0.15(1.25) = 0.2725; input = 47.5 x 2.842 x 0.2725 = $36.79 (+$5.07); total = $70.04.
Whether that applies depends on a harness decision: WITH a rolling breakpoint on the growing tail, most of the slice IS cache writes (→ ~$70); with only a static prefix breakpoint, the tail is simply uncached at 1.0x (→ ~$65). REPORT AS A BAND: $65-$70 per ticket, and the discriminating question is breakpoint placement.
NOTE THE DIRECTION: this correction makes output a SMALLER share of the bill (33.25/70.04 = 47.5%), not larger. The headline claim survives either way — output is 47.5-51% of the bill on 5% of volume.
DO NOT SUM THIS with the "20-block lookback could cost $90/ticket" risk; they are different objects and each lens presents its own as though it were the whole story.

STEP 6 — POST-SEPTEMBER RESTATEMENT (5 weeks out; the price rise is verified and dated).
At Sonnet 5 standard rates ($3/$15), holding the 28%/22% blend: input = 0.280(55.81) + 0.720(33.49) = $39.74; output = 0.220(62.50) + 0.780(37.50) = $43.00; total = $82.74. Output share = 52.0%.

STEP 7 — THE LEVER THE ARITHMETIC ACTUALLY POINTS AT.
Retry/wastage at 1.3-1.5x on $64.97 = $84.46-$97.46 effective, i.e. $19.49-$32.49 PER TICKET OF PURE WASTE. - THE 4-BREAKPOINT BUDGET IS OVERSUBSCRIBED ACROSS FOUR INDEPENDENTLY-RECOMMENDED TECHNIQUES — no single lens caught this because each proposed its own layout in isolation. - COMPRESSION DESTROYS CACHING — the interaction the brief asked me to investigate, and it is real, quantified and decisive. At 85% hit on Opus 5 the effective input multiplier is 0.85(0.1) + 0.15(1.25) = 0.2725x base. A scheme that makes the prefix VARY per call forfeits the cache entirely and pays 1.0x on 1/r of the tokens, so break-even requires r > 1/0.2725 = 3.67x compression merely to draw level with doing nothing. LLMLingua-2's published range is 2-5x — marginal at best before quality is considered. Independently corroborated: CAPC (arXiv:2607.15516) states query-aware compression 'mechanically invalidat[es] the prefix-strict cache on every call' and measured that it only beats naive caching at r>=6. CONCRETELY: a stable 100k-token prefix costs $0.05/call at Opus 5 cache-read rates; compressed 2x to 50k but varying per call it costs $0.25/call — a 5x INCREASE for half the tokens. THE ORGANISING DISTINCTION: a STATIC rewrite (caveman mode, terser system prompts) is byte-identical every call and is cache-SAFE but low-yield; DYNAMIC per-query compression is high-yield on paper and cache-HOSTILE in practice.
- COMPRESSING A PROMPT BELOW THE MINIMUM CACHEABLE LENGTH IS A SILENT 10x PRICE INCREASE — the best conflict in the set and, as W4d noted, one that appears in no blog post or paper I or any lens could find. Verified minimums: 512 tokens on Opus 5, 1,024 on Sonnet 5. Verified failure mode: 'no error is returned.' Compressing a 1,200-token Sonnet 5 subagent system prompt to ~600 tokens moves that block from 0.1x to 1.0x base input. For this product's architecture specifically — a FLEET of small specialist subagent prompts on Sonnet 5 against a 1,024-token floor — this is a realistic and completely invisible own-goal, and it is caused by doing exactly what the caveman advice recommends. GUARDRAIL: assert every intended-cacheable prefix exceeds the model minimum, and alert when cache_creation_input_tokens and cache_read_input_tokens are both zero. Source: https://platform.claude.com/docs/en/build-with-claude/prompt-caching
- CONTEXT EDITING vs CACHING — three lenses derived three different break-even formulas; they agree in DIRECTION and I recommend adopting one. W4b's closed form is the clearest: N = (w-1)(T/C) - w, where w is the cache-write/read ratio (12.5 at 5m TTL, 20 at 1h), T is total context and C is tokens cleared. Clearing 33% needs ~22 turns at 5m TTL to repay the invalidation; 50% needs ~10.5; 80% needs ~2. W4c's equivalent (remaining_turns > 12.5 x retained_prefix/N) and W4a's inequality are consistent with it. THE RULE THAT SURVIVES ALL THREE: CLEAR BIG, CLEAR RARELY. Frequent small clears are a cost INCREASE that reads as a saving on the token counter. AND THE VENDOR'S OWN DEFAULTS FAIL THIS TEST: the verified API default leaves clear_at_least UNSET, so clearing can fire and invalidate the prefix for an arbitrarily small gain; the cookbook's 15,000-against-100,000 suggestion is a T/C ratio of ~6.7, needing ~64 turns at 5m TTL to break even. Both are tuned for context-window survival, not for cost. Sources: https://platform.claude.com/docs/en/build-with-claude/context-editing | https://platform.claude.com/docs/en/build-with-claude/prompt-caching
- OBSERVATION MASKING CONFLICTS WITH CACHING TWICE OVER, WHICH GUTS ITS HEADLINE FOR THIS STACK. W4e recommends a rolling mask window (M~10) on the strength of the JetBrains ~50% cost reduction. Two interactions kill most of that here. (1) A ROLLING mask boundary REWRITES one historical block EVERY TURN, which under Anthropic's exact-prefix rule invalidates the cache from that point forward on every single turn — strictly worse than periodic large clears, and it demands a breakpoint at the mask boundary, which the budget above cannot spare. (2) The tokens masking removes are mid-history observations that at 85% hit sit in the CHEAPEST class you own ($0.668/MTok effective), whereas the paper's headline was computed on cache-blind Alibaba list pricing. NET: adopt the paper's QUALITY findings (masking beat summarisation on solve rate in most configs, and summarisation lengthened trajectories 15%); do NOT expect the ~50% dollar figure to reproduce on Anthropic pricing.
- CACHE ENGINEERING AND OUTPUT REDUCTION ARE COMPLEMENTS, NOT COMPETITORS — and this reframes the whole prioritisation. Output's share of the bill is a FUNCTION of cache success: at 0% caching output is ~21% of the bill, at 85% it is ~51%, at 95% it would be higher still (the per-token ratio runs 5.0x at h=0, 9.1x at h=0.5, 21.3x at h=0.85, 34.5x at h=0.95). So improving caching MECHANICALLY RAISES the dollar value of every output-token intervention. Two consequences: (a) there is no trade-off to arbitrate — do cache work first because it is the only class with zero quality risk, then output work, and the second gets more valuable because you did the first; (b) cache work SATURATES. Past ~90-95% hit rate the remaining money is in output tokens and in eliminating failed runs, not in further cache engineering. W4a's framing that the owner's observation is 'correct and understated' is right.
- MOVING WORK TO SUBAGENTS SAVES THE PARENT AND COSTS THE SYSTEM — the brief's third named interaction, and the answer is genuinely two-sided. IT SAVES: carrying X extra tokens in the Opus orchestrator for N remaining turns costs X x N x $0.50/MTok, so a 50k exploration carried through 200 turns costs ~$5.00 versus ~$0.15 for a 1.5k digest — roughly an order of magnitude for exploration-heavy subtasks. IT COSTS: Anthropic's measured multipliers are 4x (agent vs chat) and 15x (multi-agent vs chat), and Opus 5 'delegates to subagents more readily than prior models' so the default behaviour over-spends. IT LOSES INFORMATION: the digest boundary is lossy by construction and the orchestrator cannot audit a 'done' claim from a 1-2k summary. RESOLUTION: delegate only genuinely large independent tracks (the vendor's own cap instruction says 'Do not delegate work you can finish yourself in a handful of tool calls, and do not use subagents to verify or double-check your own work'), and pair every digest with a filesystem artefact — test output, git commit — the orchestrator can verify independently. For a product promising 'complete and TESTED', trusting the summary is the failure mode.
- SUMMARISATION-BASED CONTEXT MANAGEMENT ATTACKS THE LARGEST COST LEVER IN THE WRONG DIRECTION. The retry/wastage multiplier is worth $19.50-$32.50 per ticket — more than the entire realistic yield of every compression technique in the five lenses combined. The only measured evidence bearing on it says the obvious fix makes it worse: LLM summarisation lengthened mean trajectories 15% (52 turns vs 44) because summaries 'mask signs of a failing trajectory, encouraging the agent to persist in unproductive loops', and critic-enhanced summarisation produced 'even longer trajectories' with 'no improvement in solve rate'. Anthropic's server-side compaction is the same mechanism, and Anthropic publishes no measured quality or convergence data for it. DO NOT enable compaction on convenience grounds and assume it is neutral; A/B it against plain observation masking on completed tickets, and build an out-of-process loop detector rather than expecting a better summary to help. Source: https://arxiv.org/abs/2508.21433
- FREEZING EFFORT TO PROTECT THE CACHE CONFLICTS WITH ESCALATING EFFORT ON HARD SUBTASKS — and the resolution is architectural. Changing effort or thinking configuration invalidates the messages cache on every model, so the cache discipline requires effort to be pinned for the lifetime of a conversation. But the natural quality instinct is to escalate effort mid-run when a subtask looks hard. These cannot both be satisfied in one thread. RESOLUTION: choose effort PER SUBAGENT ROLE AT DISPATCH, and route mechanical turns (triage, dispatch, formatting, log classification) to SEPARATE low-effort threads rather than lowering effort inside the main one. The cost constraint and the quality constraint happen to demand the same topology. Two compounding facts: effort:'high' is byte-equivalent to omitting it on Opus 5, so it is safe to set explicitly; and effort does NOT reliably shorten visible responses on Opus 5, so response length needs a separate prompt instruction. - THE 1-HOUR TTL RECOMMENDATION IS WEAKER THAN W4a AND W4e PRESENT IT, BECAUSE READS REFRESH THE CACHE FOR FREE. Both lenses recommend ttl:'1h' as a near-default for a 5-hour run. Now that refresh-on-use is confirmed verbatim, the correct statement is narrower: turn count and run duration are IRRELEVANT to expiry — only idle gaps matter. A 5-minute TTL survives a 5-hour, 680-call run indefinitely provided no gap between consecutive calls on that thread exceeds 5 minutes. The 1-hour TTL is INSURANCE against tool-execution stalls (npm install, docker build, full test suite, rate-limit backoff), and it is cheaper the moment a prefix would otherwise expire and be rewritten more than 1.6 times. Since no lens found any published measurement of tool-gap distributions in autonomous coding agents, this is a decision that must be made from the owner's own telemetry: log the wall-clock delta between consecutive calls per thread and plot the tail. Do not buy the 2.0x write premium on a hypothesis.
