# Prior art for ticket-in, unattended, multi-agent, self-improving software builds

## 1. Headline

**No system in the 48 profiled does all three things at once.** The owner's question is a conjunction: ticket in, completed unattended by multiple cooperating agents, and getting better from its own runs, with real evidence. Every profiled system satisfies at most two legs, and the third is always either absent by design or refuted by the refuters. The closest thing to leg one is OpenAI Symphony (`https://github.com/openai/symphony`, Apache-2.0, 26,999 stars, last substantive commit 2026-08-12), which polls a tracker, claims an issue, spawns one Codex session per issue in a per-issue workspace, and opens a PR. Its SPEC.md says plainly that "This specification does not require a single approval, sandbox, or operator-interaction model", and the refuter confirmed from the full Elixir module listing that there is no persistence, memory, corpus, critic or judge module anywhere in the tree: learning across runs is not merely unimplemented, it is structurally absent. Gas Town (`https://github.com/gastownhall/gastown`, 17,897 stars, main frozen since 2026-07-23) and Zeroshot (`https://github.com/the-open-engine/zeroshot`, v6.46.0 on 2026-08-29) are the other two that reach leg one; both are self-graded and neither learns. Leg two, cross-run learning without fine-tuning, has **no verified evidence at all**: ReasoningBank (`https://arxiv.org/abs/2509.25140`, ICLR 2026) has three independent negative replications on its own issue tracker, one of which measured memory making the agent worse (No Memory 50.05% vs ReasoningBank 45.99% on 187 WebArena-Shopping tasks, issue #11, 2026-06-01); SWE-Exp's only "independent" corroboration is a self-citation by the same first author reporting per-repository regressions larger than its aggregate gain; AHE has two independent reproductions, both negative, and one of them places harness evolution *below* plain parallel sampling under matched budgets (67.4 versus 72.3 average pass@1, arXiv 2607.12227, v1 2026-07-14, v2 2026-08-27, figures from v2). Leg three, non-self-graded verification, is where the real evidence lives, and it is where this repository is ahead of every profiled builder system.

Two facts change what we should build next, and both are runtime constraints rather than research findings. First, **Claude Code agent teams do not spawn under `-p` or the Agent SDK**: "In non-interactive mode with the -p flag, including Agent SDK sessions, Claude doesn't spawn teammates" (`https://code.claude.com/docs/en/agent-teams`, read 2026-09-02), confirmed verbatim by two independent refuters. Every seat we run is a `-p` subprocess, so the lead-plus-teammates-sharing-a-task-list pattern the owner asked about is unavailable in our runtime, and the shared task list is conditional even when it is available: agents without the Task tools fall back to messages, and the Task tools plus TodoWrite are withheld by default on Opus 4.8, Sonnet 5, Fable 5 and Mythos 5 since v2.1.233 unless re-enabled by `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`, `--allowedTools`, `--tools`, or the Agent SDK's `allowedTools`/`tools` options. That last route matters to us, because every seat is an SDK or `-p` call. Second, the **Workflow tool does run under `claude -p` and the Agent SDK**, executes as a JavaScript script outside the conversation context, and has a working example in the wild (retro-harness ships `.claude/workflows/retrospection.js`, a ~490-line workflow with a 16-concurrent-agent cap, `https://github.com/wbopan/retro-harness`, last commit 2026-06-12). Its documented constraint bites our plan seat directly: "No mid-run user input. Only agent permission prompts can pause a run. For sign-off between stages, run each stage as its own workflow." Worth noting as a calibration on the whole pack: nothing scored fit 5, and the only three fit-4 entries are two benchmarks and a vendor report with no code released.

## 3. Approach deep-dives

### 3.1 PatchDiff: the only artefact in the pack whose evidence grade fully holds

**What it does.** Takes a tool-generated patch and the human ground-truth patch for the same SWE-bench Verified instance, instruments both builds, and asks an LLM to write a test that passes under one and fails under the other. A surviving differentiating test flags the patch as suspicious. Applied retrospectively to 877 already-submitted patches from three leaderboard tools (`https://arxiv.org/abs/2503.15223`, v2 2025-09-09).

**The pipeline as implemented.** Syntactic filter dropping patches identical to the oracle; dual instrumented builds; three-stage localisation (top-3 files, then function or class, then line range) feeding the generator a plus-or-minus-10-line window; 10 samples per target function; a bounded repair loop capped at 2 iterations; a call-trace filter discarding tests that invoke non-target functions; a flakiness gate; then human adjudication.

**Topology and coordination.** None. A deterministic Python harness making stateless `litellm` calls, plus two human adjudicators. Explicitly Agentless-style, no planning, no tool loop.

**Verification and builder influence.** The oracle is the human developer's patch, which the tool that produced the candidate never saw and cannot modify, and the differentiating tests were written after the candidate was frozen. This is a *temporal* seal, not an architectural one, and the refuter corrected the profile on exactly this point: nothing in the harness enforces the separation, so the seal does not extend forward now that the augmented suites are public.

**Learning.** None. Nothing persists between instances. The paper *proposes* accumulating differentiating tests into the benchmark suite over time; that is unimplemented and gated on manual curation.

**Evidence and its limits.** ICSE 2026, confirmed from the paper's own ACM reference footer ("2026 IEEE/ACM 48th International Conference on Software Engineering (ICSE '26), April 12-18, 2026, Rio de Janeiro, Brazil"), which contradicts the profile's own "venue UNCONFIRMED". Results: 7.8% of plausible patches (68/877) fail the full developer suite; 29.6% (260/877) are behaviourally divergent; 82.7% of the divergent ones are invisible to the full suite. Baselines are the striking part: Pynguin produced 0 differentiating tests, CoverUp produced 0, LIBRO reached 5.9%, PatchDiff 29.6%. Limits: precision on "certainly incorrect" is only 28.6% (22 of 77 human-adjudicated), 66.2% were undecidable because the issue under-specifies the requirement, the technique needs a reference implementation, and only 133 of 500 instances supported the Python 3.10+ baseline comparison. Generator strength dominates: 28.0% (gpt-4o-mini) to 47.7% (Qwen3-A22B) on the same pipeline.

**Copy.** The discrimination requirement expressed as an execution protocol rather than a review convention. Also the finding that coverage-driven generation produces literally zero differentiating tests, which tells us what *not* to ask an audit seat to do.

**Do not copy.** The flakiness gate as shipped. The refuter read the code: green requires 20/20 passes under one build, but red requires only one failure in 20 under the other, with a timeout escape hatch. Our held-out gate should require deterministic red (N of N) against a known-broken build.

### 3.2 SWT-Bench and PatchTwin+Guard: the correct semantics for an acceptance test

**What it does.** SWT-Bench grades whether an agent, given only an issue and the repository at the pre-fix commit, can write a test that fails on the buggy code and passes after the hidden gold fix, without breaking existing tests (`https://github.com/logic-star-ai/swt-bench`, NeurIPS 2024, arXiv 2406.12952).

**Pipeline.** Per-instance Docker image; apply the submitted test patch at base commit and run; apply the gold code patch and re-run; classify transitions; success requires the predicted fail-to-pass set to be a superset of the gold baseline with at least one *new* fail-to-pass, and no new pass-to-fail or fail-to-fail.

**Topology.** The benchmark has none. PatchTwin is one RepoAgent plus one Guard reviewer. The refuter established that `run_agent.py` builds a single `LiteLLMAPI` object and passes the *same* object to both, and Guard feedback is appended into the agent's own message list as a user turn. So it is one conversation with an interstitial critic call, not two agents.

**Verification and builder influence.** The grader is organiser-owned execution code and the builder never sees the gold patch. PatchTwin's Guard adds a genuine execution-anchored negative control: `check_level1` calls `clean_patch()` to remove the code patch, re-runs the test against the original repository, then restores. That half is real. `check_level2` re-runs nothing; it is same-model static review.

**Learning.** None. PatchTwin caches Guard verdicts by input hash and can replay a prior trajectory resuming from the first rejection; that is resumption, not learning.

**Evidence and its limits.** The organisers state they "have independently executed submitted predictions for verification"; PatchTwin+Guard sits at 82.9% Verified with GPT-5 (2026-07-08) and ReProAgent at 69.7% (2026-04-20). The paper's secondary finding is directly useful: filtering an agent's own candidate fixes by its own generated tests raised precision to 47.8%, "more than doubles". Limits: the harness has had no code change since 2025-09-13; issue #40 (2025-12-16) reports 14 of 433 Verified gold patches failing the harness; issue #46 (2026-02-12) reports a Django parser matching "FAILED" where Django emits "FAIL", producing false fail-to-pass classifications, with a supplied patch never merged; all five open issues have zero maintainer replies. Evaluation containers are created with no network flag, so they run on the default bridge.

**Copy.** The fail-to-pass semantics as the admission rule for every held-out assertion, and PatchTwin's strip-the-fix-and-re-run negative control.

**Do not copy.** ReProAgent's "testAcceptor". The refuter read it: `report_generator` returns `state['test_case']` with no validation and emits the final report "regardless of test status" after `MAX_FEEDBACK_TIMES=20`. It is a stage name, not a gate.

### 3.3 OpenHands: the most complete verification stack shipped, and its exact hole

Three profiles cover this lineage: the 2025 critic, the Agent Canvas console, and the V1 SDK.

**What it does.** A single-agent CodeAct loop with terminal and file-editor tools in a Docker sandbox, plus a console and a Cloud path where labelling an issue `openhands` produces a PR unattended. Optional verification layers: Stop hooks, a finish-time critic, and a goal judge.

**Pipeline.** Skills injected from `AGENTS.md`/`SKILL.md`; agent step loop with a condenser; a stuck detector every step; on `FinishAction`, Stop hooks run (exit code 2 blocks, exit 1 is treated as a non-blocking error), then the critic scores 0 to 1, then `IterativeRefinementConfig` (threshold 0.6, max 3 iterations) may auto-send a follow-up.

**Topology.** One agent per conversation. Delegation exists as a *tool*: children run in threads on the parent's `working_dir` with no worktree, the parent blocks on join, and the result is a free-text blob. The SDK paper states the limitation directly: "coordination mechanisms for multi-agent collaboration require further design".

**Verification and builder influence.** Two holes matter to us. First, the hooks that gate completion live in `.openhands/hooks.json` *in the repository the builder edits*, together with the gate script, so the builder can disarm its own gate. Second, `APIBasedCritic.evaluate()` accepts a `git_patch` argument and discards it (`# noqa: ARG002`): the critic grades the transcript, not the artefact. Issue #4554 (2026-08-20, open) shows the consequence: identical correct work scored 0.000 when done via `file_editor` and 1.000 via `terminal`, triggering a wasted refinement loop.

**Learning.** None automatic. The docs say "No automatic outcome-based learning exists". Agent-written `MEMORY.md` files are re-read automatically at session start but written at the agent's discretion with no outcome signal. The critic models are trained offline by the vendor from production traces, which is outside our constraints.

**Evidence and its limits.** The strongest datum in the whole pack for inference-time selection is that Skywork, a *different organisation*, reused the released 32B critic weights and got 38.0% -> 47.0% Bo8 on an organiser-checked entry (2025-06-16). OpenHands' own 66.4% was re-graded by the organiser to 65.8% and characterised as "essentially a best@4 number", tagged `attempts: 2+`. The 2026 rubric critic paper reports Best@8 73.8% versus Random@8 57.9% on a 148-instance mixed-outcome subset, and early stopping at threshold 0.5 giving +17.7 at 1.35 average attempts, i.e. 83% less compute (arXiv 2603.03800, 2026-03-04). The V1 SDK's MLSys 2026 "Results Reproduced" badge is scoped by its Zenodo record to SDK behaviour and event-sourcing measurements; full benchmark reproduction requires Docker and is not claimed reproduced. Only one organiser-checked single-attempt entry exists in the whole lineage (70.4%, 2025-05-24) and it is V0-era.

**Copy.** Event-sourced per-event persistence with typed exits (0.20 ms persist, 7.4 ms crash recovery on 433 conversations), the five-class stuck detector (4 identical action-observation pairs, 3 repeated errors, 3 consecutive monologue messages, 6 alternating cycles, and repeated context-window errors), the finish-time critic with a threshold and a bounded refinement count, and the early-stopping economics.

**Do not copy.** Hooks stored in the builder's own tree, and a critic that reads the transcript. Both are the exact self-grading shape our architecture exists to remove.

### 3.4 SWE-agent and mini-swe-agent: completion as a machine artefact

**What they do.** SWE-agent gives one LLM bash, a bounded file viewer and a string-replace editor inside a container and loops until `submit`. mini-swe-agent is the ~100-line successor with one bash tool, now the SWE-bench organisers' reference scaffold.

**Pipeline.** mini-swe-agent: hard budget pre-check before every model call (steps, cost, wall-clock); one `docker exec ... bash` per command with a per-command timeout, so no shell state persists; the environment ends the run when a command's stdout begins with `COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT` at return code 0, and the submission is the literal bytes after it; the trajectory is written in a `finally` after every step. SWE-agent adds a two-stage submit: the first `submit` call is intercepted by a shell tool with a stage counter that returns a checklist plus the full diff, and only a second call emits the artefact.

**Topology.** Single agent. Parallelism is only across independent benchmark instances.

**Verification and builder influence.** Grading is external and the agent never receives the fail-to-pass or pass-to-pass lists. Two holes the refuters found matter. In SWE-agent, autosubmission does **not** go through the review tool: `agents.py` runs `git add -A && git diff --cached > /root/model.patch` directly, so on `exit_cost`, `exit_context`, `exit_format` or timeout the review gate never runs at all. In mini-swe-agent, `BASH_ENV=/root/.bashrc` noise can displace the sentinel off stdout line 0, converting a real submission into `LimitsExceeded` with an empty patch (issue #938, 2026-08-16, open). That is a false *red*, the mirror image of falseFinish.

**Learning.** None in either. `.traj` files exist and are mined by *other* projects for fine-tuning; the manual demonstration path in SWE-agent is documented "Under construction" on a maintenance-only project.

**Evidence and its limits.** SWE-agent: 69.0% (345/500) organiser-checked with `attempts: 1` (2025-05-22), and HAL at Princeton PLI re-ran v1.0 in its own harness (72.0% on the 50-instance Verified Mini with Claude Sonnet 4.5 High, September 2025). mini-swe-agent: the SWE-bench organisers use it themselves; Scale footnotes its top five SWE-bench Pro rows "Run with mini-swe-agent harness" (leaderboard read 2026-09-02, entries undated) and Datacurve adopted it after a 10-task pilot (2026-05-26), while Ramp's claimed adoption could not be verified because the page renders client-side. Its Multilingual rows are `checked: true` (72.7%, 2026-02-13). The refuter could **not** confirm the 76.80% Verified figure from primary sources because `verified.html` renders client-side; the only confirmable figure is the README's self-reported ">74%". The generalisation gap is the number to remember: the same scaffold and model scores 17.67% on SWE-bench-Live's fresh post-2024 issues versus 48-69% on static SWE-bench (Microsoft, arXiv 2505.23419, 2025-05-29), and agents score 22.96% on SWE-bench-origin repositories versus 18.89% on unfamiliar ones. SWE-agent's own ablations quantify interface design: removing the lint guardrail costs 3.0 points, a full-file viewer instead of a 100-line window costs 5.3, removing search costs 6.0, removing the edit command costs 7.7.

**Copy.** Environment-detected completion; typed exit statuses persisted per step; hard budget pre-checks before each model call; stateless per-command exec inside a long-lived container; the two-stage submit checklist including its "`git checkout --` any test file you touched" clause, which is itself evidence that builder test-tampering is a routine failure mode.

**Do not copy.** Any exit path that bypasses the completion gate. Our equivalent must run the gate on budget exhaustion, not skip it.

### 3.5 Augment SWE-bench Agent: the best-documented negative result in the pack

**What it does.** A minimal single-agent scaffold that runs N independent rollouts per instance in separate containers and then has a *different* model pick the winner from the diffs alone.

**Pipeline.** Container per rollout on the SWE-bench instance image, started with an empty commit so `git diff` yields exactly the agent's changes; agent loop with a 120,000-token deterministic truncation rule that keeps the last 3 turns and replaces older tool output with a re-run hint; patch extracted as a diff; then `majority_vote_ensembler.py` shows an o1 call the problem statement plus all candidate diffs in `<candidate_solution index=i>` tags.

**Topology.** N independent rollouts, no communication, plus one post-hoc picker.

**Verification and builder influence.** In-system verification is self-graded: `complete_tool.py`'s `run_impl` asserts only that the answer string is non-empty, and the loop also ends silently on a tool-less reply. The genuine separation is external: the container is discarded and only the diff is applied to a fresh image. The refuter corrected the mechanism label: no majority is computed anywhere, there is no diff normalisation or vote tally; one temperature-0 call is asked to "Pick the majority vote solution". It is an LLM consensus judgement, not a vote.

**Learning.** None.

**Evidence and its limits.** 70.4% (352/500) pass@1, with the SWE-bench maintainer commenting "I was able to reproduce the 70.4% number" (2025-06-18). The refuter downgraded this: per the experiments README the verification step "re-grades every instance from its recorded test output ... No Docker, no re-execution", and `metadata.yaml` reads `checked: false`. So it is a maintainer log re-grade. The vendor blog's own negative findings are the valuable part and are single-source: running a separate fix-regressions agent after implementation "introduced bugs into otherwise correct solutions" for "no net improvement"; run-to-run instability such that "sampling any two rollouts over 50 examples would have different outcomes"; prompt optimisation saturates; ensembling is "too expensive to use in real-world settings"; the non-ensembled baseline was never released (issue #9).

**Copy.** Grade a frozen diff in a fresh container rather than the builder's live workspace. Never run a repair seat over a green build. The deterministic truncation rule, which needs no summariser seat.

**Do not copy.** The "majority vote" framing. If we add a consensus picker, it must be described as what it is.

### 3.6 R2E-Gym: lexicographic combination of graders

**What it does.** A training-environment factory whose transferable part is the inference-time stack: sample K rollouts, then rank them by execution-based signals first and a model critic only as a tiebreak.

**Pipeline that matters.** `create_bestofn_aggregate.py` in hybrid mode, confirmed in code by the refuter: sort by verifier probability and keep the top half, then keep the maximum regression-test pass count, then the maximum reproduction-test score, then argmax verifier probability. Regression tests come from a precomputed SWE-bench command; reproduction tests come from a separately trained testing agent whose outputs were published as a dataset and therefore never saw the candidate.

**Topology.** N independent rollouts plus two offline scoring roles that never talk to the builder. Coordination is trajectory JSONL enrichment.

**Verification and builder influence.** The hidden tests are *not* sealed from the agent: `DockerRuntime` moves `/r2e_tests` to `/root/r2e_tests` and symlinks it into `/testbed/r2e_tests`, inside the agent's own workspace. The execution-free verifier reads the full trajectory including the agent's thoughts, and removing the trajectory drops Best@K from 42.8% to 37.6%, so it scores the narrative. Independent reproduction (issue #17, 2025-08-26, unanswered) measured true-positive rate 57.8% and true-negative rate 52.0% at threshold 0.5, near chance.

**Learning.** Weights only. Not transferable.

**Evidence and its limits.** Refuted on results: there is no R2E-Gym entry in the SWE-bench experiments repository, and the profile's claim that SWE-RL's entry was organiser-checked is false (`checked: false` in metadata.yaml, as are both DeepSWE entries). What survives is the *ordering* principle: execution-only scored ~43.7%, model-critic-only ~42.8%, hybrid 51.0%. Also survives: the reward path never inspects the container exit code, and an empty parse against an empty expectation scores 1.0, which is a fail-open we must not replicate.

**Copy.** Lexicographic ordering with execution first and the model critic strictly as a tiebreak. Reproduction tests generated by a party that has not seen the candidate. SWE-smith's mutation yields as a template for building a known-bad corpus procedurally (procedural AST 40.2%, LM modify 56.0%, combine 96.9% validated-mutant rates).

**Do not copy.** Anything about hidden-test placement, and any reward function that does not read the exit code.

### 3.7 SICA: the only self-improving builder with a promotion rule worth stealing

**What it does.** A coding-agent scaffold whose outer loop benchmarks agent *i*, archives per-problem scores and traces, then runs the best prior agent on its own source with the instruction to make the system better at writing code, producing agent *i+1*.

**Pipeline.** Benchmark in Docker with 8 async workers; `select_base_agent()` computes per-iteration mean and 95% confidence interval (z=1.96, std/sqrt(n)) and, walking backwards from the current iteration, picks the first whose mean is at least the best-ever lower bound; `shutil.copytree` the base into a new directory; run the improve prompt with the archive mounted read-only; rebuild the image; repeat.

**Topology.** One orchestrator agent delegating strictly sequentially, plus a review committee on the plan and an asynchronous overseer running on a *different* model (Sonnet 3.7 while workers use Sonnet 3.5) that can cancel an agent by id.

**Verification and builder influence.** The grader is the external benchmark harness. The seal fails in one specific place the refuter found: benchmark containers mount the whole experiment directory read-write, so a solver container can overwrite any iteration's `perf.json`, and `select_base_agent()` ranks on those files with no hash or signature. Issue #4 (2026-08-04, open) ships a proof of concept that forges the ranking.

**Learning.** Yes, and it is the real thing: the persisted artefact is the agent's entire source tree per iteration, plus `description.txt` and a two-phase `agent_change_log.md` where the feature description is written at iteration *i* and the outcome at *i+1* after measurement.

**Evidence and its limits.** Refuted on results. The 17% to 53% is on a self-selected 50-problem subset with no leaderboard entry, and the run is not reproducible as shipped: the repository hardcodes `diagnose_model = 'o1-2024-12-17'` and Claude 3.5 Sonnet (New) for self-modification, neither of which is a live model as of 2026-09. The paper also records path dependency, with 4 of 15 iterations regressing and poor early feature suggestions lowering the quality of later ones. The refuter also found that the hard-gated utility function the profile praised is computed but unused: `score_type` defaults to `mean_score` in the promotion path.

**Copy.** The confidence-interval promotion rule (promote only if the candidate's mean is at least the lower bound of the best ever seen; ties keep the incumbent) and the two-phase change log. Both are directly applicable to §5.2's repair loop and §8's corpus.

**Do not copy.** The claim that it gates on budget adherence, and the writable score ledger.

### 3.8 SWE-Marathon: closest published analogue to our ticket shape

**What it does.** Twenty ultra-long-horizon tasks, 2 to 10 hours of agent wall-clock against expert human estimates of 40 to 400 hours. Five are product clones (Slack, Mastodon, Excel, S3, Stripe) scored by shell tests plus a Playwright and computer-use UI rubric. That is one ticket, one whole application, sealed hidden verifier. That is our shape.

**Pipeline.** Task authoring with a written list of reward-hack risks; a three-criterion approval gate; CI with static verifiers; an oracle/no-op baseline run where the oracle must score 1.0 *through the real verifier* and the no-op must score 0.0, "if it passes, the task is broken"; empirical piloting where three frontier-agent trials must each burn at least 25M tokens and over an hour before being allowed to fail; an adversarial cheating agent (`/cheat`); human ship/fix/not-ready approval. Then rollouts in Modal sandboxes, hidden verification, an agentic UX stage, reward combination, and a post-hoc GPT-5.5 trajectory audit.

**Topology.** The solver is single-agent across 13 configurations. The *evaluation* stack is deliberately multi-model.

**Verification and builder influence.** The hidden verifier is never materialised in the workspace and scoring reads the submitted container state, "not the commands or intermediate reasoning used to reach it". Two refuter corrections matter to us. First, the reward blend is `binary_reward = 1 if correctness >= 1.0 and ux >= 1.0` in `cua_blend.sh`; the `0.5*correctness + 0.5*ux` the profile quotes is diagnostic-only `partial_score` in `metrics.json`. Carry the AND, not the blend. Second, on the five product clones, which are the tasks closest to ours, the UX critic is `anthropic/claude-opus-4-7` while the solver set includes claude-opus-4-7 and 4-8. That is Claude grading Claude, on exactly the shape our taste critic has. Also: the verifier runs inside the container the agent controlled and bootstraps from agent-authored `requirements.txt`/`package.json`.

**Learning.** None. The 800 GB trace corpus is raw material for someone else's loop.

**Evidence and its limits.** The paper's own numbers (best 26.3% pass@1) are stale; xAI's Grok 4.6 model card (2026-08-12, revised 2026-08-17) publishes a v1.1 table footnoted "Results reported are taken from evaluations conducted by Abundant AI", topping at Opus 5 50.0%. That is a frontier lab republishing organiser-run numbers, the strongest external verification in the pack short of a neutral re-run. The failure taxonomy is the payload: of 526 agent-attributable failures, Implementation Failure 41.6%, Timeout 31.4%, Reward Hacking 15.4%, Premature Termination 7.6%, Poor Self-Verification 4.0%, and **99.6% carry a validation-failure signal**, meaning better local testing could plausibly have exposed the defect before submission. Reward hacking is 13.8% attempt-tier and 10.2% shipped bypasses with 0 of 1,300 earning reward, and the authors state the audit "cannot catch behavior tuning that leaves no trace, so the rates are lower bounds". Degradation with run length is monotonic on three of five scaffolds (claude-code 41.9% -> 3.2% across tool-call quintiles), the lowest-token quintile passes 11.3% against the highest at 8.3%, and context compaction tracks failure: 0 of 71 reward-bearing terminus-2 summariser trials pass, against 8.9% without.

**Copy.** The oracle/no-op two-sided baseline; MIN-over-channels; scoring the artefact state; the adversarial cheat sweep before freeze; the "built out evenly" check comparing progress where tests look against where they do not.

**Do not copy.** Their UX critic's model choice, or running the verifier inside the builder's container.

### 3.9 NL2Repo-Bench: spec derivability and gate negative controls

**What it does.** 104 tasks, each a real Python library reverse-engineered into a single ~1,200 to 1,500-line requirements document. One agent gets that document in an empty workspace and must produce an installable package. The grader is the upstream repository's own pytest suite, hidden from the agent.

**Verification and builder influence.** Structurally sealed in the important sense (tests are in the grading image, never in the workspace, and grading runs after the agent exits), but not hermetic: browsing is enabled, there is no `--network=none` at grading time, and builder-written tests outside the declared cleanup paths survive and are collected.

**Evidence and its limits.** Refuted. The headline 40.2% (Claude Sonnet 4.5 in Claude Code) is not reproducible from the released artifact, which ships only an OpenHands 0.56 path. More usefully, the harness audits are a catalogue of gate defects we must not reproduce: the `boto` grading image has no pytest so 1,014 cases score zero for every model (issue #15); more-itertools' 682 cases never run and fastapi-users' 556 collapse on a broken import printed in the spec itself, while funcy's hidden tests call 28 symbols with zero occurrences in the 1,428-line specification (issue #17); `shlex.split` without a shell silently no-ops setup commands in 7 of 104 tasks (issue #13). Verdict extraction is a first-match substring on the final assistant message.

**The number to carry, and why it is directional only.** Revealing the tests to the same agent lifts it from 40.2% to 59.4% average and from 3 to 18 fully passed repositories. That is the size of the gap our visible/held-out split is measuring, but it must be carried as directional evidence rather than a target, for three reasons the fact-check surfaced: the ablation appears in the paper body and not in the abstract, so it is not independently confirmable from the abstract; the profile's results lens is refuted, because the 40.2% headline is not reproducible from the released artifact; and the v2 abstract's own claim that "even the strongest agents achieve below 40% average test pass rates" sits in tension with the 40.2% baseline the delta is measured from. What issue #17 does establish separately is that a large part of the gap is spec under-derivability rather than builder weakness.

**Copy.** A spec-derivability check before freeze: every symbol, route or selector a held-out assertion depends on must have a hit in the frozen ticket and plan text; zero-hit assertions are spec defects, not builder failures. Also the three-state termination taxonomy: declared DONE, stalled-awaiting-input (GPT-5 hit 84.5% "Non-Finish", halting for guidance that never arrives), and timed out.

**Do not copy.** Substring verdict parsing, and hand-declared test denominators that disagree with what the runner collects.

### 3.10 CAID: the only controlled measurement of builder decomposition

**What it does.** A manager agent reads a repository or paper, builds a dependency graph, emits a JSON delegation plan, and spawns N engineer agents, each in its own `git worktree` on its own branch. The manager then merges each branch and bounces conflicts back.

**Topology and coordination.** Lead plus workers, one level, strictly file-mediated: JSON task assignments out, `git commit` plus a structured result record back. Engineers run as asyncio coroutines. The refuter confirmed genuine concurrency and genuine worktree creation, and corrected two things: the released code defaults engineer iterations to 50, not the paper's 80, and there is a single Docker workspace shared by all engineers with isolation provided at the git-worktree level rather than container-per-agent.

**Verification.** Self-graded against the repository's own visible tests, and the manager runs **no** tests after merging; merge acceptance is `git merge` succeeding. The fallbacks are worse than the default: `git merge -X theirs` and a commit-on-behalf path for uncommitted engineer work, both confirmed verbatim in code.

**Learning.** None.

**Evidence and its limits.** Refuted on results (no organiser verification, single run per configuration, author-chosen gpt-5-mini judge, and a within-configuration swing of 8.7% versus 34.3% on one task). But the isolation ablation is the single most decision-relevant number in the pack for us: on PaperBench, single agent 57.2, worktree isolation 63.3, **soft isolation 55.5**, where prompt-level "do not overlap" instructions performed *worse than one agent*. On Commit0-Lite the same ordering holds (53.1 / 59.1 / 56.1). The scaling result is equally sharp: `simpy` scored 0.0% at N=2, 92.1% at N=4 and 44.3% at N=8, with the collapse attributed to the manager splitting functions of the same file across engineers. And the headline "+25.6" is the weakest model's delta; the frontier deltas are +6.1 and +6.0, against +5.8 from simply doubling the single agent's iteration budget on Commit0.

**Copy.** If we ever split the builder: enforce isolation with git and the OS, never with prompt text; start at 2, not 4; require the plan seat to emit a file-ownership map and refuse assignments that give two seats the same file.

**Do not copy.** Merging without re-running the gate, `-X theirs`, and committing a worker's uncommitted diff on its behalf.

### 3.11 retro-harness (RHO): an offline self-improvement loop with a real gate shape

**What it does.** A single-pass, label-free optimiser for an agent's harness. Selects a diverse-and-hard coreset of past tasks, re-solves each three times under the current harness, has the same model write a structured diagnosis, spawns N optimiser agents that each edit a copy of the harness, re-solves the coreset under each candidate, and accepts the argmax only if the mean pairwise preference score is strictly greater than zero.

**Topology.** Script-orchestrated fan-out. Ships as a Claude Code dynamic workflow (`.claude/workflows/retrospection.js`, 16-concurrent cap) and a Codex script, which is the direct evidence that this shape runs under a headless CLI.

**Verification.** Acceptance is same-model pairwise self-preference: the judge sees the task, both harnesses and both trajectories, presents the candidate first and negates the score to counter position bias, and cannot execute code. The paper's own Section 6.3 calls it "a conservative selector rather than a perfect ranker": a non-chosen candidate scored 0.85 where the chosen one scored 0.78.

**Learning.** Yes: the harness directory itself is the persisted artefact, re-materialised into every future solve. Single round only; the paper makes "no claim that gains compound or even remain monotonic across multiple rounds".

**Evidence and its limits.** Refuted on results: the 0.78 is on a self-generated deterministic hash split of the SWE-Bench Pro public set and is absent from Scale's leaderboard (whose best is 61.50%). One retrospective round costs 103 optimisation agent calls and about 3.2 hours end-to-end at 10-way concurrency, which is the figure to plan against; the "$500 and 4 to 6 hours per iteration" figure that circulates alongside RHO belongs to Meta-Harness, not to this system. The ablations are the durable part: DPP coreset selection 0.78 versus random 0.64, coverage-only 0.58, difficulty-only 0.62, against a 0.59 baseline; and full diagnosis 0.78 versus raw trajectories 0.60, versus **0.56 with the self-consistency cue removed, which is below the 0.59 vanilla baseline**. That last figure is the important one: a weakened diagnosis signal made the accepted harness *worse than doing nothing*, and the strict mean-greater-than-zero gate did not prevent it.

**Copy.** The structured diagnosis format (per-rollout issues, cross-rollout inconsistency, one task-agnostic improvement direction, severity as a soft attention weight) and the requirement that a repair be graded by re-solving, not by review.

**Do not copy.** Same-model pairwise preference as the acceptance gate, and the fail-neutral scoring the refuter found: `evaluate.py` returns a score of 0 on any parse or execution failure and `loop.py` accepts on `mean > 0` with no quorum of valid scores, so a coreset of ten with nine unusable judgements and one +1 accepts.

### 3.12 Claude Code agent teams: the shape the owner asked about, and why it is unavailable

**What it does.** An experimental mode where one interactive session is a fixed team lead that spawns N full Claude Code sessions as teammates, coordinating through a shared task list under `~/.claude/tasks/{team-name}/`, where `team-name` is `session-` followed by the first eight characters of the session ID. The docs state only that "Task claiming uses file locking to prevent race conditions"; the per-file layout that circulates elsewhere is third-party reverse-engineering, not documented. Per-agent JSON mailboxes carry messages between agents.

**The blocker.** "Spawning teammates also requires an interactive session. In non-interactive mode with the -p flag, including Agent SDK sessions, Claude doesn't spawn teammates." Every seat in our console is a `-p` subprocess. Two refuters confirmed this verbatim from the docs.

**Further constraints the refuters established.** The shared task list is conditional: "Agents without the Task tools coordinate through messages instead of the shared task list", and the Task tools plus TodoWrite are withheld by default on Opus 4.8, Sonnet 5, Fable 5 and Mythos 5 since v2.1.233 unless re-enabled by `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`, `--allowedTools`, `--tools`, or the Agent SDK's `allowedTools`/`tools` options. There are no nested teams. Teammates share the lead's working directory, and the docs state plainly that "Two teammates editing the same file leads to overwrites."

**Verification.** No built-in grader. The only hard gates are user-authored hooks: `TaskCompleted`, `TeammateIdle`, `SubagentStop` and `Stop`, all vetoing on exit code 2 with stderr fed back as feedback.

**Learning.** None. The task-list directory persists for `/resume`; the team config is deleted at exit.

**Evidence and its limits.** There are no task-success numbers for this feature. Every published figure is cost or latency (the costs page says "approximately 7x more tokens than standard sessions when teammates run in plan mode"). The docs' own Limitations section documents our co-primary metric: "teammates sometimes fail to mark tasks as completed, which blocks dependent tasks" and "The lead can stop early too, deciding the team is finished before all tasks are actually complete."

**What is available to us instead.** Named subagents under `-p` with `isolation: worktree`, `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` (default 3), `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` (default 20) and `maxBudgetUsd` per seat; `SendMessage` between named subagents without agent teams enabled; and the Workflow tool, which runs under `-p` and the Agent SDK as a JavaScript script outside the conversation context, with the constraint that there is no mid-run user input and sign-off between stages requires running each stage as its own workflow. The provenance rule is worth adopting verbatim: a message from another agent is tagged as not-from-the-user, "A teammate can't approve a permission prompt or supply consent on your behalf".

**Copy.** Exit-code-2 completion vetoes wired to the sealed gate result; per-seat budget caps; worktree isolation for subagents; the message-provenance rule.

**Do not copy.** Any design that assumes teammates exist in our runtime.

## 5. Lessons to adopt, ranked

**1. Two-sided seal baseline before freeze: oracle 1.0, no-op 0.0, through the real gate.**
Source: SWE-Marathon (`https://swe-marathon.org`, arXiv 2606.07682, 2026-06-05). Evidence: its approval gate requires the reference solution to score 1.0 *through the actual verifier* and a no-op agent to score 0.0, with the review guide stating "if it passes, the task is broken"; reviewers must also "remove no-op tests and placeholder assertions" and "ensure dependency failures hard-fail rather than silently skip". Corroborated in the negative by NL2Repo-Bench, where the `boto` grading image has no pytest and 1,014 cases score zero for every model (issue #15), and by UTBoost's released dataset containing an instance the gold patch itself cannot pass (issue #1, 2026-07-22). Change: at freeze/seal, run the held-out half against the bare scaffold (expect all red, deterministically) and against a plan-seat reference stub (expect green); quarantine any assertion failing either direction and record the quarantine in the seal manifest. Risk: authoring a reference stub costs a seat call per ticket, and a bad stub could quarantine good assertions; mitigate by only quarantining on the *no-op passes* direction at first, which needs no stub.

**2. MIN over verification channels, and score the artefact state, not the transcript.**
Source: SWE-Marathon, corrected by its refuter: `cua_blend.sh` computes `binary_reward = 1 if correctness >= 1.0 and ux >= 1.0`, and scoring reads "the submitted container state, not the commands or intermediate reasoning used to reach it". Counter-evidence for the alternative: OpenHands' `APIBasedCritic.evaluate()` discards the git patch and grades the transcript, producing 0.000 versus 1.000 for identical correct work depending on which tool wrote the file (issue #4554, 2026-08-20). Change: judge seat combines sealed-gate result, taste critic and human-factors adversary with MIN semantics rather than a weighted blend, and every critic receives the rendered artefact and gate log, never the builder's transcript. Risk: MIN makes the taste critic load-bearing, so a flaky critic can floor a genuinely green run; mitigate with the tri-state below.

**3. An adversarial cheat seat against our own frozen suite, before the seal.**
Source: SWE-Marathon's `/cheat` sweep (132 shipped verifier bypasses across 1,300 trials, 0 successful) and SWE-bench Pro's failure to do it (100% of public images leak the gold fix via git history; 21% of Opus 4.6 runs mined it per mini-swe-agent issue #787, 2026-03-18; fix PR #94 unmerged). Change: add a cheat seat to the adversarial audit stage that is given the visible half and a workspace and is scored on whether it can turn the held-out half green without building the feature; any success is a blocking suite defect. Also audit our builder workspace for the git-history channel specifically. Risk: an unproductive seat that finds nothing on most tickets; bound it hard by budget and only run it on the first freeze of a ticket.

**4. Grade a frozen diff in a fresh container, not the builder's live workspace.**
Sources: Augment (container discarded, only `git diff` applied to a fresh image) and the Darwin Gödel Machine, whose `swe_bench/report.py` calls `remove_patches_to_tests()` so that agent edits to test files never reach the scorer; TRAE's `trae_agent.py` strips test-directory hunks the same way. R2E-Gym is the counter-example that shows what the rule prevents: its `DockerRuntime` moves `/r2e_tests` to `/root/r2e_tests` and symlinks it into `/testbed/r2e_tests`, inside the agent's own workspace. Further evidence for the fresh container: SWE-Marathon's verifier runs inside the container the agent controlled and bootstraps from agent-authored dependency files; CAID merges without re-running anything. Change: the sealed gate should snapshot the builder's workspace as a diff against the frozen base and apply it to a clean image, rather than mounting the workspace. Risk: our artefacts are whole applications, not patches, so "diff against base" is larger and slower than in the patch setting; the mitigation is a content-addressed workspace snapshot rather than a literal patch.

**5. A spec-derivability check on every held-out assertion.**
Source: NL2Repo-Bench issue #17 (2026-08-19), where funcy's hidden tests call 28 symbols with zero occurrences in the 1,428-line specification and fastapi-users' 556 cases collapse on a broken import printed in the spec itself; and the tests-visible ablation showing 40.2% -> 59.4%. Carry that ablation as directional only: it comes from a benchmark whose headline is not reproducible from its released artifact, and whose v2 abstract reports below-40% average pass rates, in tension with the 40.2% baseline the delta is measured from (see §3.9). Change: at the adversarial audit stage, require every selector, route, string literal and identifier a held-out assertion depends on to have a hit in the frozen ticket plus plan text; zero-hit assertions are spec defects routed back to the spec seat, not builder failures. Risk: over-zealous matching rejects legitimate inferred criteria; keep it as a finding class the audit must answer rather than an automatic rejection, consistent with the existing audit trail.

**6. Never run a repair seat over a green build; and add a "fails on base too" negative control before spending a fix iteration.**
Sources: Augment's blog (`https://www.augmentcode.com/blog/1-open-source-agent-on-swe-bench-verified-by-combining-claude-3-7-and-o1`, 2025-03-31), where a post-implementation fix-regressions agent "introduced bugs into otherwise correct solutions" for no net gain; Cursor Cloud Agents' auto-fix skip rules (`https://cursor.com/docs/cloud-agent/capabilities`, read 2026-09-02), which include "The same check is already failing on the base commit of the PR" plus a hard cap of 10 CI follow-ups and a stop-if-human-pushed rule. Change: the fix seat may only be triggered by a red held-out signal, and before each iteration the failing check is run against the pre-build baseline; if it is already red there, classify as environmental and route to a separate lane with its own budget. Risk: none material; this narrows an existing loop.

**7. Fail-closed verdict parsing with a collected-count assertion.**
Sources: mini-swe-agent issue #938 (2026-08-16, open), where `.bashrc` noise displaces the completion sentinel and a real success is recorded as `LimitsExceeded` with an empty patch; SWE-bench PR #620 (merged 2026-08-14), which records the test exit code and refuses to grade a run whose exit code is non-zero but whose parsed output shows no failures; NL2Repo-Bench's first-match substring parsing (`https://arxiv.org/abs/2512.12730`, 2026-01-08). A fourth pointer is worth chasing but is not yet evidence: Terminal-Bench's `_is_resolved` returning `all()` over an empty result set, so an empty parse would be a pass, is reported in BenchJack's appendix (`https://arxiv.org/abs/2605.12673`, 2026-05-12), but both BenchJack lenses were refuted and no refuter independently confirmed that code reading, so treat it as an unverified pointer to inspect in Terminal-Bench directly. Change: the sealed gate consumes Playwright's JSON reporter, asserts the collected test count equals the sealed manifest count, treats any missing test id as red, and emits a distinct `inconclusive` state for "suite did not run" that never maps to pass. Risk: more red verdicts from infrastructure noise, which is why the tri-state matters.

**8. Make DONE a machine artefact with a two-stage gate, and close the bypass.**
Sources: mini-swe-agent's environment-detected sentinel (the run ends when a *command's stdout* starts with the sentinel at return code 0, and the submission is the literal bytes after it); SWE-agent's `review_on_submit_m` two-call gate with a `SUBMIT_STAGE` registry, where `-f` is not exposed to the model; and its hole, found by the refuter, where autosubmission runs `git add -A && git diff --cached` directly and never invokes the tool, so on budget exhaustion the review never happens. Also Symphony's workpad completion bar (checklist complete, acceptance items checked, tests green, external checks green, no outstanding comments). Change: the builder's DONE becomes a structured result file with a machine-checkable completion bar plus explicit `blockers` and `nextSteps`; a non-empty blockers list short-circuits before the gate spends a run; and the gate runs on every exit path including budget exhaustion. Risk: a builder learning to write empty blockers lists; the sealed gate remains the only pass signal, so this is a cost saving rather than a verdict.

**9. Extend the anti-loop with duplicate-tool-call and diff-hash-recurrence classes, plus a no-progress counter.**
Sources: SWE-Marathon (`https://arxiv.org/abs/2606.07682`, 2026-06-05), where 32% of terminus-2 tool calls repeat an earlier (function, arguments) pair and the highest-duplication scaffold produced 63 of 83 wall-clock timeouts; OpenHands' five-class stuck detector, including the alternating-pair (A,B,A,B over 6 cycles), consecutive-monologue and repeated-context-window-error classes (`https://docs.openhands.dev/sdk/guides/agent-stuck-detector.md`, read 2026-09-02); karpathy/autoresearch's ratchet, where the loop kept a random-seed change worth +0.0004 against a ~1e-3 noise floor because there was no noise gate (`https://news.ycombinator.com/item?id=47291123`, 2026-03-07); Symphony's silence-based stall timer, `stall_timeout_ms` default 300000, reset on event (`https://github.com/openai/symphony` SPEC.md, read 2026-09-02). Change: add to the fix seat's fingerprint store a hash of the workspace diff per attempt (stop on 5 identical, and on A-B-A recurrence at distance >= 2), a duplicate-tool-call counter, a silence timer per seat, and a `no_progress_turns` budget dimension measured as turns since the held-out or visible failure count last decreased. Risk: false aborts on legitimately slow phases; the silence timer must reset on any event, not on wall-clock.

**10. Adopt ReasoningBank's corpus *shape* while treating its results as refuted.**
Source: `https://arxiv.org/abs/2509.25140` (ICLR 2026) and `https://github.com/google-research/reasoning-bank`. Evidence for the shape, independent of the headline: two distinct extraction prompts (success-specific and failure-specific), a hard cap of 3 distilled items per run, top-1 retrieval with same-project exclusion, and an injection block that instructs the agent to "explicitly discuss if you want to use each memory item or not" so uptake is observable. The retrieval ablation is the load-bearing number: k=1 49.7, k=2 46.0, k=3 45.5, k=4 44.4, so more retrieved memories monotonically hurt. The failure-trajectory ablation shows distilled failures help (46.5 -> 49.7) while storing raw failed trajectories degrades a comparable system (44.4 -> 42.2). Add the leave-one-ticket-out guard from issue #17. Change: our §8.2 injection should default to one exemplar per seat with a same-ticket exclusion and an observable-uptake instruction, and §8.1 stream B should store distilled failure lessons rather than raw trails. Risk: the results are refuted, so we must treat any gain as unproven and keep §8.3's held-out-class negative control as the only evidence that the corpus does anything.

**11. Confidence-interval promotion for self-repair, and a two-phase change log.**
Source: SICA's `select_base_agent()` (z=1.96, promote the first iteration whose mean is at least the best-ever lower bound, walking backwards) and its `agent_change_log.md` where the feature description is written at iteration *i* and the outcome at *i+1* after measurement. Counter-evidence for raw argmax: RHO's strict `mean > 0` gate accepted a harness that scored 0.56 against a 0.59 vanilla baseline when the diagnosis signal was weakened. Change: §5.2's repair loop promotes only on a paired, per-case improvement on the targeted known-bad fingerprints plus a CI-lower-bound check on the aggregate, and every repair carries a hypothesis recorded before the gate and an outcome recorded after. Risk: with a small known-bad corpus the interval is wide and almost nothing promotes; that is the correct failure direction.

**12. Symphony's retry taxonomy and lifecycle coupling.**
Source: `https://github.com/openai/symphony` SPEC.md: a worker exiting normally gets a 1 s re-check of authoritative state and continues the *same* thread with short continuation guidance; a worker that fails or stalls gets `min(10s * 2^(n-1), 5 min)` backoff; every retry re-reads state first and releases the claim if the task is no longer active; stall detection is silence-based; and PR #97 (2026-07-17) couples worker and scheduler lifecycles under a `one_for_all` supervisor after a duplicate-dispatch bug where workers outlived the scheduler state that claimed them. Change: our supervisor should distinguish "seat finished a turn, work remains" from "seat crashed", and a dashboard restart mid-run must not leave a seat acting on a run whose claim was lost. Risk: low; this is orchestration hygiene.

**13. A structured escalation exit for the fix seat.**
Source: the escalation-channel study (`https://arxiv.org/abs/2608.29460`, 2026-08-29). Adopt the *mechanism* only: a `report_suite_defect` tool with four required fields (issue type including `test_infrastructure_conflict`, problem assessment, approaches tried, recommendation) whose response is a fixed receipt that reveals nothing about validity. Do **not** cite its effect size: the results lens refuted it because 8 of 14 models were selected in for having at least 8% baseline hacking and then re-measured, which is regression to the mean, and the mechanism lens found the SHA-256 tamper check running inside the agent's own container and the receipt telling the agent "No further attempts are needed". Change: give the fix seat a way to say "this held-out assertion is not derivable from the ticket" that parks the run into `awaiting_input` with the four fields rendered in the dashboard, rather than burning its budget. Risk: the builder learning to escalate instead of building; cap escalations per run and count them.

### 5.1 Lessons not to adopt

- **Claude Code agent teams as a builder topology.** Unavailable under `-p`, experimental, disabled by default, no task-success evidence, and its own docs document early-stopping and missed task completions.
- **"Change the topology, not the prompt."** This appears in MAST's Appendix H.3 as a conclusion "for both systems", and MAST's own Table 5 refutes it for AG2: improved prompts scored 89.75 versus 85.50 for the new topology on GPT-4, and the topology change was not significant (Wilcoxon p=0.4). It holds for ChatDev only.
- **AHE-style harness evolution as a headline strategy.** Two independent reproductions are negative. The first (arXiv 2607.12227, v1 2026-07-14, v2 2026-08-27; figures from v2) is budget-matched and additionally places it below plain parallel sampling, 67.4 versus 72.3 average pass@1, with held-out gains of +1.2 and +0.0. The second, HarnessCompass (arXiv 2608.01918, 2026-08-03), reports 66.0 for itself at 5 turns against 63.0 for AHE at 20 turns and 60.4 versus 54.7 on held-out tasks; it is negative for AHE but is neither budget-matched nor equipped with a parallel-sampling comparator.
- **DSPy, MIPRO, TextGrad and any optimiser needing thousands of scored programmatic LM calls.** Our seats are CLI subprocesses; this is already ruled out in our own research doc and nothing in the pack changes it.
- **Any critic that reads the builder's transcript.** R2E-Gym's execution-free verifier loses 5.2 points when the trajectory is removed, i.e. it is scoring the narrative; OpenHands' critic discards the patch entirely.
- **LLM-judge rubric scores as a pass gate.** SWE-Marathon's UX stage is `_aggregate()` over PASS/PARTIAL/FAIL verdicts with a `ux >= 1.0` requirement, so an LLM holds a unilateral veto on a "deterministic" reward; WebGen-Bench's judge is the same model family as the in-loop tester.
- **Best-of-N with a same-model preference judge as the acceptance rule.** RHO's own data shows the picker choosing 0.78 over a sibling at 0.85.
- **Fine-tuned critics, reward models and any weights-based learning.** R2E-Gym, OpenHands' critic, SWE-Gym, DeepSWE, WHALE. Excluded by the no-fine-tuning constraint.
- **The "topology beats scaffold" framing of parallel writers on a shared workspace.** CAID measured prompt-level isolation at 55.5 against a 57.2 single-agent baseline, and Gas Town, Cursor and the C-compiler run all report the same convergent-edit collapse.
- **Adding more visible tests in response to a bad run.** Nothing in the pack supports it, and NL2Repo-Bench's tests-visible ablation measures the size of the gap rather than a remedy.

## 6. What nobody has solved

Stated plainly, with no hedging.

1. **Unattended acceptance of a self-modifying pipeline's own patches.** Every self-repair system in the pack either has a human merge gate (Symphony's Human Review, Gas Town's planner, Cursor's PR review) or has no gate at all (Ralph, autoresearch). SICA is the closest, and its score ledger is writable from the containers it grades (issue #4, 2026-08-04).
2. **Cross-run learning with a verified positive effect and no fine-tuning.** Zero systems. ReasoningBank has three negative replications, SWE-Exp's corroboration is a self-citation with per-repository regressions, AHE is below parallel sampling under matched budgets in the one reproduction that measured it that way, RHO claims one round with no compounding, and Meta-Harness searched and evaluated on the same 89 tasks.
3. **Multiple writers sharing one workspace for a greenfield build.** CAID's soft isolation scored below a single agent; the OpenHands SDK paper states coordination "requires further design"; Claude Code's own docs say two teammates editing the same file leads to overwrites.
4. **A grader that the builder cannot influence *and* that is itself audited.** We have the first half and the pack does not. Benchmarks have the second half partially (UTBoost, PatchDiff, BenchJack) but their graders are visible to everyone.
5. **Detecting behaviour tuning that leaves no trace.** SWE-Marathon states it outright: the audit "cannot catch behavior tuning that leaves no trace, so the rates are lower bounds". Its 10.2% shipped-bypass rate is a floor, not a measurement.
6. **A learning corpus that does not poison itself.** EvoMal's results are refuted, but its mechanism finding is unaddressed anywhere in the pack: a store written by the system that reads it is a propagation channel by construction, because a planted entry can be re-authored into a fresh, agent-named entry that survives deletion of the original. Its further claim that agents prefer copying their own prior outputs over externally planted ones could not be confirmed by the refuter from accessible sources, so do not rely on that part.

## 8. Method

Nine sweeps produced 48 candidate profiles. Each profile was built from primary sources (repository code, arXiv PDFs and HTML, vendor documentation, leaderboard metadata, issue trackers) with URLs and dates recorded per claim. Each profile was then passed to a single refuter running two lenses: **results-real** (does the claimed performance survive external verification, replication and staleness checks) and **mechanism-real** (does the system implement the multi-agent, self-learning or non-self-graded verification the profile attributes to it, confirmed from primary sources). There were zero critic rounds after the refuter pass. Where the refuter and the profile disagree, this report carries the refuter's version and says so.

The refuter pass changed the picture materially.
