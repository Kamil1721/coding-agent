# Phase 4 — Cron: the literal walk-away

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A scheduled run that starts without anyone present, refuses to overlap another, spends
against a stated ceiling, records what it did whether or not it did anything, and is readable in one
file the next morning — or fails with a named reason and a non-zero exit rather than quietly not
happening.

**Architecture:** The OS scheduler (launchd on this machine; `crontab` shown as the portable form)
invokes **one short-lived process, `cron-tick`**. A tick does not build, does not gate, does not
supervise, and above all **does not construct an `Orchestrator`**: its only channel into the run
pipeline is loopback HTTP against the dashboard that is already running. It holds a single-flight
lease, asks the server what is already in flight, claims at most **one** queued ticket by an atomic
rename, `POST`s it with `designLock: "auto"`, writes a journal row on every exit path including the
ones where it did nothing, refreshes a report, and exits with a code that says which of eight things
happened. The dashboard's own machinery — the queue in `pump()`, `reconcileOnBoot`, the bounded
GATE/FIX loop, the design-lock timer, `verdict.md`, `assumptions.md`, `backlog.md` — is unchanged and
is what makes an unattended run mean anything. This phase adds the trigger, the bound, and the
account of it.

**Tech Stack:** TypeScript 5.9.3 strict (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`,
`verbatimModuleSyntax`), Node ≥24, `node:test`, `node:fs` (`open(…, "wx")`, `rename`), global
`fetch`. **No new npm dependencies. No new SQL table.** Two additive `runs` columns already exist and
are unwritten; this phase writes them.

**Spec:** `docs/superpowers/specs/2026-07-28-orchestration-canvas-design.md` §12 (why cron is Phase 4
and not sooner), §16.1/§16.3/§16.4 (the grader is the reason cron is allowed to exist at all), §17.3
rules 1-5 (and rule 2 is the load-bearing one).

## Why this phase has no spec section, and what stands in for one

Every other phase implements a numbered section. **Cron has none.** It appears in the spec three
times and never as a design:

- §16 owner framing: *"I would rather just build it and walk away, or have it run on cron. Key is to
  have this self-improving and managing itself with little to no need for me to do anything."*
- §16.1: *"On cron this compounds — every scheduled run accumulates another confidently-wrong
  result."*
- §12: *"`POST /api/runs` already exists, so scheduling is a handful of lines — but **cron plus an
  untrustworthy gate is automated disappointment**, accumulating confidently-wrong builds nobody
  reads. Schedule only after the gate loop has earned it."*

So the spec's contribution to this phase is a **precondition and a warning**, not a mechanism. The
precondition is met: Phase 2d shipped the bounded loop (`gate-fix-loop.ts`, four reachable stops) and
the backlog that is written on every terminal outcome. The warning is what THE TRAP below is derived
from, and §17.3 rule 2 is the only hard requirement the spec states about a scheduled run:

> **2. Cron runs auto-select by default.** A scheduled run that parks forever waiting for a click is
> the exact failure unattended operation exists to avoid. `POST /api/runs` accepts
> `designLock: "auto" | "ask"`, defaulting to `auto` when the request is not interactive.

"Scheduling is a handful of lines" is true of the `POST`. It is not true of the six failure modes in
THE TRAP, which is the whole of this phase's difficulty.

## Global Constraints

- **A tick never constructs an `Orchestrator` or opens `runs.db`.** Enforced by the shape of its
  dependency type (Task 8), not by a comment. At the API level two submissions are a *queue*
  (`pump()` starts one run and positions the rest); at the *process* level two Orchestrators against
  one `runs.db` is corruption — both would `pump()`, both would pick the same queued row, and two
  builders would run in one workspace. That is the case being designed out.
- **Overlap is a REFUSAL, not a queue.** The tick does not enqueue behind a live run. An unattended
  scheduler that enqueues on every tick accumulates work nobody asked for and spends a shared
  rate-limit window on it.
- **Every exit path appends at least one journal row.** A tick whose only observer is a file it
  writes itself has no other observer. This is not a nicety; it is the phase.
- **Exit code is part of the contract.** 0 for "submitted" and for a deliberate no-op; a distinct
  non-zero for each way of not working, so `launchd`'s `StandardErrorPath` carries what the journal
  carries.
- **The tick validates nothing the server already validates.** Ticket length, model availability,
  body shape: the server has one validator each and returns a named error. The tick records the
  server's own message. A second validator is a second answer to drift away from.
- **No dollar figure, anywhere.** `costUsd` is `null` for subscription runs by invariant
  (`db.ts:9-13`, `http.ts:153-157`, `api-types.ts`). Cron's ceiling is denominated in **runs per
  window**, and the run-level bounds are **turns and calls**. A cron report that printed dollars
  would be the fabrication `api-types.ts` forbids.
- **No live metered call in any test.** `fetch` is injected everywhere. The Gemini/Veo path is
  reached by nothing in this phase.
- **Never read, echo or log a key value.** The tick's journal records `dashboardUrl`, `modelId`,
  decisions and reasons. It records no environment dump.
- `bakeoff/` untouched. `dashboard/STATUS.md` and `bakeoff/STATUS.md` untouched by these tasks. No
  AI-attribution trailer. No `--amend`. No `git push`. `git commit -F - -- <explicit paths>` only.

**Run every command from `dashboard/server`.** Siblings are editing this tree; compile to a private
outDir at the same depth so nobody clobbers anyone's `dist/`:

```bash
npx tsc -p tsconfig.json --outDir dist-cron && node --test "dist-cron/**/*.test.js"
```

**The depth is not free-form.** `contract-parity.test.ts` resolves the client package as

## THE TRAP — read this before writing any code

**A cron run that fails silently is worse than no cron at all** — and the mechanism is specific
enough to build against:

> **A tick's only observer is a file it writes itself. Six of the seven ways a tick can end produce
> the identical observable — "no new run appeared" — and cron's stdout goes nowhere.**

| What actually happened | What the owner sees the next morning |
|---|---|
| the dashboard was not running | no new run |
| `DASHBOARD_PORT` differs between the server and the plist | no new run |
| the lease was left behind by a killed tick | no new run, forever |
| a ticket was claimed and the tick died before the `POST` | no new run, and the ticket is gone from the queue |
| the `POST` was rejected (unknown model, unavailable model, oversized ticket) | no new run |
| **the schedule was never installed / never fired** | no new run |
| **the queue was empty — nothing was supposed to happen** | no new run |

Only the last row is correct behaviour. Every row above it is a fault, and every one of them is
**observationally identical** to it. That is the same shape as the twelve recorded instances in
`STATUS.md §6`: a check that can only observe success. Here the check is the *absence* of a run, and
absence is what both success and failure look like.

**The rule, and it is not negotiable:**

```
every terminal path of a tick             →  exactly one journal row naming the DECISION and WHY
                                          →  a distinct non-zero exit code, except for
                                             "submitted" and a deliberate no-op
a tick that submitted                     →  an INTENT row before the POST and an OUTCOME row after
an intent with no outcome                 →  reported as such, and counted against the ceiling
the tick never ran at all                 →  NOT detectable from inside a tick. Only a READER
                                             comparing `now` to the last row can see it, so the
                                             report computes staleness at READ time, and the
                                             OVERDUE arm has its own test.
```

`decision: "skipped"` and a silent exit produce the same number of new runs and **must never produce
the same record**. Tasks 3, 8 and 9 own this, and their negative controls are mandatory rather than
advisory: delete the journal write from one arm and watch that arm's test go red, with the red output
recorded.

**The second half of the trap, and it is the one that reads as fine.** §16.1 is explicit that the
compounding failure of cron is not a crash — it is *"another confidently-wrong result"*. A tick that
submits successfully every night, against a gate that could not run, produces a shelf of green-looking
runs with `heldOutPass: null`. So the report in Task 9 may never render `null` as anything a reader
could mistake for a pass, and `gateStopReason` must actually be persisted (Task 7) or every run in
the report reads "no outcome recorded" forever.

### Task 1: One port resolver, so the tick cannot knock on the wrong door

**Why first:** trap row 2. `index.ts` resolves the bind port with a **private** `parsePort` and
`DEFAULT_PORT` from `http.ts`; a tick that re-derived either would drift the first time one changed,
and the symptom is `ECONNREFUSED` at 03:00 — trap row 1 wearing row 2's clothes. And the tick cannot
import `http.ts` at all: `http.ts` imports `describeError` from `./orchestrator.js`, which is the
module graph this phase is keeping out of the tick.

**Files:**
- Create: `dashboard/server/src/dashboard-url.ts`, `dashboard/server/src/dashboard-url.test.ts`
- Modify: `dashboard/server/src/http.ts` (replace two `export const` with one re-export)
- Modify: `dashboard/server/src/index.ts` (delete the private `parsePort`, import it)

- Consumes: `DASHBOARD_ENV` from `paths.ts`, `BakeoffError` from `bakeoff/dist/contracts.js`.

### Task 2: The single-flight lease — and what it does NOT protect

**Why:** trap row 3, and the honest statement of the overlap question. Two things are being kept
apart, and conflating them would put a fabricated justification in the code:

```
AT THE API LEVEL          two POSTs while a run is active are a QUEUE. pump() starts one and
                          positions the rest; workspaces are per-run (runs/<id>/workspace).
                          Safe, but not WANTED — see Task 4.
AT THE PROCESS LEVEL      two Orchestrators against one runs.db is CORRUPTION. Both pump(), both
                          claim the same queued row, two builders in one workspace. This is what
                          the tick's dependency type (Task 8) makes unreachable.
AT THE TICK LEVEL         two ticks in the same minute would both claim, both journal, and both
                          spend a ceiling slot. That is what THIS lease prevents.
```

**Files:**
- Create: `dashboard/server/src/cron/cron-lease.ts`, `dashboard/server/src/cron/cron-lease.test.ts`

  taken before the journal was writable.
- Produces:

  | "submitted"      // a run exists now
  | "skipped"        // deliberate no-op: nothing queued, or a run is still in flight
  | "refused"        // the ceiling is spent
  | "lease-held"     // another tick is running
  | "stranded"       // a claimed ticket from a dead tick is unresolved
  | "misconfigured"  // the config refuses to produce a submission
  | "unreachable"    // the dashboard did not answer, or the model is unavailable
  | "rejected";      // the dashboard answered and said no
export interface CronRow {
  readonly tickId: string;
  readonly at: string;
  readonly phase: "intent" | "outcome";
  /** Null on an intent row: at intent time the outcome is not known. */
  readonly decision: CronDecision | null;
  readonly reason: string;
  readonly ticketFile: string | null;
  readonly runId: string | null;
  readonly exitCode: number | null;
  readonly dashboardUrl: string;
  readonly modelId: string | null;
}
export const CRON_JOURNAL_FILE = "journal.jsonl";
export function appendIntent(dir: string, row: Omit<CronRow, "phase" | "decision" | "exitCode" | "runId">): void;
export function appendOutcome(dir: string, row: Omit<CronRow, "phase">): void;

  readonly rows: readonly CronRow[];
  /** Lines that did not parse. Reported, never silently dropped. */
  readonly unreadableLines: number;
}
export function readJournal(dir: string): JournalRead;
export function windowRows(rows: readonly CronRow[], now: string, hours: number): readonly CronRow[];
/** Intent rows in the window. THE CEILING COUNTS THESE. */
export function intentsInWindow(rows: readonly CronRow[], now: string, hours: number): readonly CronRow[];
/** Intents with no outcome row for the same tickId — a tick that died mid-submit. */
export function orphanIntents(rows: readonly CronRow[]): readonly CronRow[];
export function lastRow(rows: readonly CronRow[]): CronRow | null;

### Task 4: The policy — overlap is a refusal, and the ceiling is a count of runs

**Why pure:** every rule here is a decision about spending the owner's quota while they are asleep,
and a decision that can only be observed by spending is a decision nobody checks. `decideTick` takes
data and returns a verdict; the tick does the IO.

**The rules, and the reason each one is not the obvious alternative:**

| Rule | Decision | Why not the alternative |
|---|---|---|
| any run is non-terminal (`queued` / `running` / `awaiting_input` / `rate_limited`) | `skipped` | Enqueueing behind it is safe at the API level and wrong at the intent level: an unattended scheduler that enqueues on every tick builds a queue nobody asked for and spends one shared rate-limit window on all of it. |
| the newest run is `rate_limited` | `skipped`, naming the window | Submitting into an exhausted 5-hour window gets the new run throttled too. The existing run is resumable and is the better use of the window. |
| intents in window ≥ ceiling | `refused`, with the count and the window | A ceiling that logs instead of refusing is a comment. |
| the queue is empty | `skipped`, "nothing queued" | This is the ONE legitimate no-op, and it must be a *recorded* one — it is trap row 7 and the only row that is not a fault. |
| otherwise | `submit` with the ticket file | — |

Order is load-bearing: **overlap is checked before the ceiling**, so a night where a run is still
building does not burn ceiling slots on refusals.

**Files:**
- Create: `dashboard/server/src/cron/cron-policy.ts`, `dashboard/server/src/cron/cron-policy.test.ts`

**Interfaces:**
- Consumes: `RunSummary` and `ApiRunStatus` from `api-types.ts` (type-only — the wire shape
  `GET /api/runs` returns), `CronRow` from Task 3.
- Produces:
```ts

### Task 5: The claim — one atomic rename, and a stranded claim halts loudly

**Why:** trap row 4. The gap between "the ticket left the queue" and "a run exists" is where an
unattended scheduler loses work, and the loss is invisible: the file is simply not in `queue/` any
more.

The directory layout under `<cronRoot>/`:

```

submitted/   settled: `<runId>-<name>` — the run id is in the filename, so the ticket that produced
             a run is findable from either end.

journal.jsonl Task 3.
report.md    Task 9.

### Task 9: The report — what happened while you were asleep, and "cron never ran"

**Why the renderer takes `now` as an argument:** the tick writes the report, and a tick can only write
it when it runs. So a report that computed its own staleness could never say "cron has not ticked in
three days" — the one failure that has no observer inside the system at all (trap row 6). The
renderer therefore takes `now`, and there are **two callers**: the tick (whose `now` is the tick's own
clock) and a read-only entrypoint the owner runs when they wake up (whose `now` is now, so the OVERDUE
arm is reachable).

**What it must surface, and every item already exists — this task connects them, it does not invent
them:**

| Surface | Where it comes from |
|---|---|

| the ceiling: used / allowed / window | `intentsInWindow` |
| queue depth, stranded claims, failed tickets | `cron-queue.ts` |
| intents with no outcome | `orphanIntents` |
| a damaged journal | `JournalRead.unreadableLines` |

| `backlog.md`, `assumptions.md`, `design-lane.json` | files the run already writes, named by path |

## The six questions this phase had to answer

1. **What triggers a run, and what stops two from overlapping.** The OS scheduler invokes one
   short-lived tick. Three separate mechanisms, for three different overlaps: the **lease** (two ticks),
   the **policy** (a second run over a live one — a refusal, not a queue), and the **dependency type**
   (two Orchestrators against one `runs.db`, which is the only one of the three that is corruption
   rather than merely unwanted). Stated as three because conflating them would put a false
   justification in the code: workspaces are per-run and `pump()` already serialises at the API level.
2. **What happens when nobody is watching and it goes wrong.** THE TRAP's table, eight decisions, one
   journal row each, distinct exit codes, and a report that leads with STRANDED / OVERDUE / a damaged
   journal. The bounded fix loop already writes `backlog.md` on every terminal outcome including green;
   Task 9 names it per run so the backlog is surfaced rather than buried.
3. **Quota and cost bounds.** No dollar arm exists (`costUsd: null` by invariant), so the bounds are
   turns, calls and runs. What already exists, with the arithmetic:

   | Bound | Value | Where |
   |---|---|---|
   | turns per `build()` call | **400**, no env override | `claude-builder.ts:208`, `:759` |
   | build calls per run | ≤ 2 segments + (cap − 1) fix rounds = **≤ 4** at the default cap | `orchestrator.ts:821-824`, `gate-fix-loop.ts:183-188` |
   | ⇒ turn exposure per run | **≤ ~1600 builder turns** | the product of the two above |

## CONCERNS — where this plan believes the system is wrong, and builds to it anyway

1. **The DESIGN lane's image spend is the one ceiling that is not a mechanism.** "max 2 retries" is a
   sentence in a prompt (`design-prompt.ts:37` and `:103-105`, quoting `taste-frontend-expert.md:46`), and
   `imageCalls` is counted **after the fact** by string-matching the script name in the `tool` sink
   (`orchestrator.ts:973-980`). Every other bound in the table above is enforced; this one is
   *observed*. It is also the only path that spends **cash** rather than subscription quota. Under the
   owner's eye that is tolerable. On cron it is the single place spend can run away, and a plan that
   listed ceilings without naming the one that is not a ceiling would be the exact shape this
   repository records twelve times. Not fixed here — enforcing it belongs where the calls are made, in
   another wave's file — and `DASHBOARD_CRON_MAX_RUNS_PER_WINDOW` bounds how many *runs* can reach it,
   which is a bound on the multiplier and not on the multiplicand.
2. **There is no per-run turn budget, only a per-call one.** 400 turns × up to 4 build calls is a
   product nothing in the system computes or caps, and `boundsFor()` in `agent-shortlist.ts` returns
   per-agent turn caps that still have **no production caller** (Phase 2b NOT COVERED item 4, §11 item
   3). A run that is quietly looping burns the shared rate-limit window until the 4-hour wall clock or
   the provider stops it. Cron makes that happen while nobody is watching. The honest mitigation
   available today is the run *count*, which is what this phase bounds.
3. **`DASHBOARD_CRON_MAX_RUNS_PER_WINDOW` counts runs, not work.** Four trivial tickets and four
   portfolio rebuilds cost wildly different amounts of the same window. A token-based ceiling is
   available in principle (`runs.input_tokens` etc. are persisted) and is not attempted here, because a
   ceiling on a number the report cannot explain is worse than a coarse one it can.
4. **Fail-closed on a stranded claim halts all cron work until a human intervenes.** That is chosen
   deliberately — the alternative is guessing whether a `POST` landed, and guessing wrong means a
   duplicate build — but it means one killed tick stops the scheduler until the owner reads the report.
   The journal's intent row plus `GET /api/runs` makes the question answerable in one look, which is
   the most that can be done without the server telling us whether it saw the request.
5. **A stale `dist/` is another invisible failure, and this plan does not close it.** The plist runs
   `node dist/cron/cron-tick.js` and deliberately does not build (a tick that runs `tsc` into the
   shared `dist/` while siblings compile is worse). So an un-rebuilt fix runs silently as the old code.
   No mechanism is proposed; it is recorded so the next reader does not discover it at 03:00.
6. **The lease's liveness check is `process.kill(pid, 0)`, and pids are reused.** A recycled pid reads
   as ALIVE, so a genuinely dead tick's lease survives until its TTL expires — up to 15 minutes of
   refused ticks, each of which journals `lease-held` and is therefore visible. The failure direction
   was chosen: refusing while a lease *might* be live costs a tick; breaking a live one costs a
   duplicate claim.
7. **`http.ts` importing `describeError` from `orchestrator.ts` is why Task 1 exists at all.** The
   router pulling the run pipeline in for one error formatter is a coupling nobody would design; it
   makes "share the port constant" impossible without either a new module or dragging the orchestrator
   into a scheduler. Task 1 takes the new module. The coupling itself is untouched.
8. **The interactive design lock is broken end to end, and Phase 4 is where that becomes visible.**
   `lockManifest` wants a workspace path; the wire carries a copy in the screenshots directory. Nobody
   noticed because **nothing has ever parked** — `designLock` is dropped by the route, so the whole
   `awaiting_input` branch, the cards, the resume body and `lockManifest`'s path validation have been
   dead code in production since they shipped. That is the same class as the twelve recorded instances:
   four correct components joined into a path no test drove end to end. This phase does not fix it (it
   is another wave's seam, and `mockups[].path` vs `refs[].path` is a wire-contract decision), but
   Task 6's precondition makes it **blocking** rather than latent, and refuses to ship a park that
   cannot be unparked.
9. **`interactive` now means two things.** `designLockInteractive` defines it as "a person at the
   dashboard" for §17.3 rule 2, and Task 6 makes that real. It is *not* "created by cron": a `curl`
   from the owner's own terminal is non-interactive and not scheduled. Nothing in this phase marks a run
   as cron-created on the row — the journal's `runId` is the join — and if a later phase wants
   "which runs did cron make?" in SQL, that is a `created_by` column and a migration, not a re-reading
   of `interactive`.

## Things this plan could not determine from the repo

1. **Whether `launchd` reliably runs a missed `StartCalendarInterval` job at wake on this OS version.**
   Vendor-documented, unmeasured, and it decides whether a laptop that sleeps through the schedule
   catches up or skips. The report's OVERDUE line makes either behaviour visible after the fact.
2. **What a sane default ceiling is.** 4 runs / 24 h is a *guess*, chosen because it is small enough
   that a bad night is cheap and large enough to be useful. Nothing has measured how much of a 5-hour
   window one portfolio build consumes, and until something has, this number has no evidence behind
   it — only a direction.
3. **Whether the queue-file model matches how the owner actually wants to feed cron.** A directory of
   plaintext tickets was chosen for its atomic claim, not from a stated preference. If the real want is
   "one standing ticket, re-run nightly, improving the same artefact", that is a different phase: the
   claim becomes a *copy*, `strandedClaims` loses its meaning, and the ceiling becomes the only bound.
4. **Whether a run submitted while `awaiting_input` is genuinely unsafe or merely unwanted.**
   `reconcileOnBoot` sets `awaiting_input` for any run whose builder died with the server, and such a
   run holds no lock and no subprocess. The policy treats it as in-flight anyway, because resuming it
   is the better use of the window than starting a rival — but that is a judgement, not a measurement.
5. **Whether the owner-managed queue file needs protection this plan does not give it.** Redaction
   happens at the store boundary (`db.ts:507-548`), so a secret pasted into a queue file is redacted on
   the way into `runs.ticket_text` and into the run's own files — and is **not** redacted in the queue
   file itself, in `claimed/`, or in `submitted/`, which are plaintext on disk under the owner's home.
   That is the same exposure as any file the owner writes, and it is stated rather than implied.
