## 1. The icon set

### 1.1 What was rejected and why

No icon library. `lucide-react` is not installed and must not be. Nothing here is hand-authored SVG
path data: a model emitting `<path d="M12 2L3 7…">` never sees what it drew. Every mark below came
out of the Gemini raster pipeline, was downscaled to its true 24px, nearest-neighbour upscaled 10x,
and **looked at** before it was accepted. The evidence is in §1.5.

### 1.2 The idiom

Flat geometric drafting marks: square corners, blunt line ends, no rounded caps, no taper, no
gradient, no shadow, no perspective. The family carries **two registers deliberately**, and the
product already uses the same split (`globals.css`: a role is "a dull 3px rule", a state is "a
saturated filled chip"):

- **Structure marks** (Overview, Files) are hairline outlines — they depict a thing that contains a
  structure.
- **Act marks** (Chat, Result, Activity, Questions) are solid mass — they depict something that
  happened or is being asked.

Optical size is held constant instead of stroke width: every glyph's ink box fills 80% of its square
frame (the mask pipeline enforces this arithmetically, `side = max(w,h)/0.8`).

**Relationship to the two assets already in `public/`.** `pre-build-empty.png` and
`pre-build-sealed.png` are canvas *illustrations* — hairline node rectangles on the dot grid with a
single accent rule. This set **extends** that language (same hairline rectangles, same square
corners, same flat monochrome) and does not supersede it. Nothing about those two files changes.

### 1.3 Colour: the icons have none

Every asset is a **white RGBA glyph whose alpha is the drawing**. It is used as a CSS mask, so the
paint is `currentColor` and the rail's own state rules do all the tinting. Consequences that matter:

- One asset per mark per DPI. No light/dark or rest/hover variants.
- The icons **cannot fight `roles.ts`**, because they never carry a hue. The seven role hues stay
  the exclusive property of the canvas.
- WCAG: at rest the mark is `--color-ink-dim` `#a2abbb` on `--color-surface` `#11141a` = **9.6:1**.
  Hover/active `--color-ink` `#e7eaf0` on the same = **13.9:1**. Both pass AA for non-text graphics
  (3:1) with large margin.

### 1.4 The assets

All shipped, on disk now, under `dashboard/public/rail/`. Sizes are 1x / 2x / 3x of a 24px box.

| Rail entry | asset stem | files | what the mark is |
|---|---|---|---|
| Overview | `overview` | `overview-24.png`, `overview-48.png`, `overview-72.png` | landscape card, solid filled band across the top edge, two rules below |
| Chat | `chat` | `chat-24.png`, `chat-48.png`, `chat-72.png` | two offset rectangular speech blocks, upper-left solid, lower-right outline |
| Files | `files` | `files-24.png`, `files-48.png`, `files-72.png` | vertical spine with three branch stubs, each ending in a small square |
| Result | `result` | `result-24.png`, `result-48.png`, `result-72.png` | a heavy check stacked over a heavy cross, no container |
| Activity | `activity` | `activity-24.png`, `activity-48.png`, `activity-72.png` | four stacked bars of differing length, each with a leading solid square |
| Questions | `questions` | `questions-24.png`, `questions-48.png`, `questions-72.png` | one heavy question mark with a square dot |

**Result deliberately does not assert success.** A lone tick would claim "passed" on a run that
failed, and this product's whole value is that it tells the truth about what it did. Check-over-cross
says "outcomes", not "good outcome".

### 1.5 Legibility evidence — what was regenerated, and why

The loop was: generate → alpha-extract → downscale to 24px → nearest-upscale 10x → read the PNG →
judge. A 24px PNG read directly tells you nothing; the upscale is what has eyes in it.

| Mark | passes | verdict |
|---|---|---|
| Chat | 1 | Accepted first pass. Solid+outline pair reads at 24px, silhouette unlike anything else in the set. |
| Files | 2 | First pass accepted. A second, heavier-stroke pass (`files-b`) was generated to even out weight; **rejected** — its spine ran past the last branch and the top stub attached ambiguously. Original kept. |
| Activity | 1 | Accepted first pass. |
| Questions | 1 | Accepted first pass. A `?` is a glyph, not a picture, and it was still generated as raster like the rest so it could be checked at 24px alongside the others. |
| Overview | 2 | **Regenerated.** Pass 1's "solid top band" came back as two thin rules and the card read as weightless next to the solid marks. Pass 2 (flush filled band) accepted. Pass 3 at heavier stroke was generated and **rejected** — the band came back inset and floating, which read as "a rectangle inside a rectangle" rather than a card. |
| Result | 4 | **Regenerated three times.** Pass 1 came back as a clipboard with a clip band, cluttered at the top and the muddiest mark in the set. Pass 2 obeyed "no container" not at all. Pass 3 (check + cross side by side, no container) read cleanly but its ink box was 792x314 — squat, so after squaring it was optically half the size of its neighbours. Pass 4 stacks the two marks vertically (ink box 450x769); it is bolder, squarer and the clearest mark in the set. Accepted. |

Nothing in the set was shipped as mush, and nothing needed a text fallback.

The build pipeline, recorded because it will need to be re-run when a mark is added:

```
gemini-image.sh "<prompt>" -a 1:1 [-i style-plate.png] -o raw/<name>.png
# then: greyscale -> normalise -> alpha = 1 - luminance (Gemini returns black-on-white)
#       -> trim to ink -> centre in a square where the ink fills 80%
#       -> lanczos3 downscale to 24 / 48 / 72 -> PNG
```

### 1.6 How the implementer paints them

Verified by rendering it in Chromium against the real palette, not asserted:

```css
.rail-icon {
  width: 24px; height: 24px;
  background-color: currentColor;            /* the button's colour paints the glyph */
  -webkit-mask-image: image-set(url("/rail/chat-24.png") 1x, url("/rail/chat-48.png") 2x, url("/rail/chat-72.png") 3x);
          mask-image: image-set(url("/rail/chat-24.png") 1x, url("/rail/chat-48.png") 2x, url("/rail/chat-72.png") 3x);
  -webkit-mask-size: 24px 24px;  mask-size: 24px 24px;
  -webkit-mask-repeat: no-repeat; mask-repeat: no-repeat;
  -webkit-mask-position: center;  mask-position: center;
}
```

Both the `-webkit-` and unprefixed properties are required; Chromium still needs the prefix for
`mask-image` in some paths and Safari needs it outright.

**Trap, hit and confirmed in this lane:** a CSS mask image will not load cross-origin or from a
`file://` page. Served from Next's own `public/` on the same origin it renders correctly (proved
below); if a future build moves these to a CDN, the CDN must send permissive CORS or the icons
silently vanish while `<img src>` of the same file still works. That exact failure was reproduced
here, so it is not theoretical.

The `<span>` carrying the mask is decorative: `aria-hidden="true"`. The accessible name lives on the
button (§3).

## 2. The rail

Vertical, pinned to the **left edge of the run view**, a flex sibling of the canvas — not floating
over it. It is chrome, so it never scrolls and never overlaps a node.

### 2.1 Geometry — every number

| Thing | Value | Note |
|---|---|---|
| `RAIL_WIDTH` | **48px** | fixed at every viewport width; the rail never collapses or hides |
| Rail background | `--color-surface` `#11141a` | one step up from the canvas, same as every other chrome surface |
| Rail right border | `1px solid --color-line` | |
| Rail vertical padding | `6px` top and bottom | |
| Button size | **48 x 44px** (full rail width) | full-bleed on purpose — see radius note |
| Button radius | **0** | The one place the app's `rounded-sm` control radius is *not* used. Measured in the mock: a rounded 44px chip inside a 48px rail leaves a 2px sliver of rail surface either side that reads as a rendering bug. A full-bleed strip is the correct shape for an edge rail. |
| Icon size | **24 x 24px**, centred | |
| Gap between buttons | `2px` | |
| Group separator | `1px` `--color-line`, `margin: 6px 10px` | inset so it does not touch the rail's own border |
| Hit area | the whole 48 x 44 button | 2112px², comfortably above the 44x44 target minimum |
| Status dot | `6px` circle, `top: 7px; right: 6px`, `box-shadow: 0 0 0 2px --color-surface` | the ring is what stops it merging into the glyph |
| Active indicator | `2px` wide, `--color-accent`, `position: absolute; left: 0; top: 8px; bottom: 8px` | flush with the rail's left edge |

### 2.2 Order and grouping

```
┌ 6px pad
│ [ Questions ]        ← reserved 44px slot; renders a button only when there is a dialogue
│ ──────────           ← separator
│ [ Overview ]         ← carries the run's status dot
│ [ Chat ]
│ [ Files ]
│ [ Result ]
│ ⇣ flex spacer
│ ──────────
│ [ Activity ]         ← pinned to the bottom
└ 6px pad
```

**The Questions slot is reserved, always.** It occupies 44px whether or not there is a dialogue. If
it were merely absent, every other icon would move 44px up and down as a run progresses, and an
icon-only rail lives entirely on position memory. An empty 44px at the top reads as padding; a
sliding rail reads as broken.

### 2.3 States — all of them

| State | Icon colour | Background | Other |
|---|---|---|---|
| Rest | `--color-ink-dim` | transparent | |
| Hover | `--color-ink` | `--color-surface-raised` | `transition: background-color 120ms, color 120ms` |
| Pressed (`:active`) | `--color-ink` | `--color-surface-raised` | `transform: translateY(1px)` |
| Selected (panel open) | `--color-ink` | `--color-surface-raised` | 2px accent bar at `left: 0` |
| Keyboard focus | unchanged | unchanged | global `:focus-visible` ring, but **`outline-offset: -2px`** |
| Disabled | n/a | n/a | no rail entry is ever disabled; an entry with nothing to show is absent, not greyed |

Hover and pressed reuse the app's own ghost-control convention verbatim
(`ui.tsx:119` — `text-ink-dim hover:text-ink hover:bg-surface-raised`). Nothing new is invented.

`outline-offset: -2px` is not a preference. The global rule in `globals.css` is
`outline: 2px solid var(--color-accent); outline-offset: 1px`, and on a button flush to the viewport
edge the outer ring is clipped by the window on its left side. Confirmed in the mock render: the
focus ring on a rail button showed as three sides. Inset it.

**Selected is double-coded** (bar + background + icon brightness) because the accent bar alone is
2px of colour on a 48px rail, and this owner's screen is where a missed selection state costs a
click into the wrong panel.

### 2.4 Status on the Overview icon

The Overview button carries a 6px dot in its top-right corner reflecting `run.status`, so a closed
rail still says how the run went. This is the one piece of the old always-visible run chip that
survives as chrome rather than as panel content.

| `run.status` | dot |
|---|---|
| running / queued | `--color-accent`, `animate-pulse` |
| awaiting_input / rate_limited | `--color-warn` |
| failed / cancelled | `--color-fail` |
| finished | `--color-pass` |

`prefers-reduced-motion`: drop the pulse, keep the colour. That is the whole of this design's motion
budget — the rail does not slide, the panel does not spring, the icons do not animate on hover.
A console that moves while you read it is a console you learn to distrust.

### 2.5 Keyboard

- The rail is `role="toolbar" aria-orientation="vertical" aria-label="Run panels"`.
- **Roving tabindex:** exactly one rail button is in the tab order at a time (the selected one, else
  the first). `ArrowUp` / `ArrowDown` move between rail buttons and wrap. `Home` / `End` jump to the
  first / last.
- `Enter` and `Space` toggle the button's panel.
- `Escape` **inside a panel** closes it and returns focus to that panel's rail button. `Escape` on
  the canvas keeps its existing meaning (clear selection) — do not add a window-level listener; the
  reason is written down at `sheet.tsx:101-107` and applies unchanged.
- Opening a panel moves focus to the panel container (`tabIndex={-1}`, focus with
  `{ preventScroll: true }`), matching `sheet.tsx:123-125`.

### 2.6 The panel

| Thing | Value |
|---|---|
| Width | **400px**, fixed, `w-[min(400px,calc(100vw-48px))]` |
| Why 400 | it is `HUD_WIDTH` (`orchestration-canvas.tsx:179`). The dock was widened to 400 on 2026-08-04 because the pre-build rows wrapped to three lines at 360. Reusing it means no content re-measures. |
| Background | `--color-surface` |
| Right border | `1px solid --color-line` |
| Header | `padding: 10px 12px`, bottom border `--color-line`. Eyebrow: `font-mono text-[9.5px] uppercase tracking-[0.18em] text-ink-faint`. Title: `text-[13.5px] font-semibold truncate`. Close: the existing ghost `Button` reading `close`, `title="Close (Escape)"`. Identical to `sheet.tsx:140-150` with the border side flipped. |
| Body | `flex-1 min-h-0 overflow-y-auto`, `padding: 12px`, `gap: 12px` between sections |
| Section card | `border border-line rounded bg-canvas`; header `font-mono text-[9.5px] uppercase tracking-[0.18em] text-ink-faint` in a `px-[10px] py-2` strip with a bottom border; body `p-[10px]` |
| Radius | reuse the app's existing `rounded` for cards and `rounded-sm` for controls. Do not introduce a third radius. |
| Resizable | **No, not in v1.** Stated so it is a decision and not an omission: a drag handle needs a persisted width, and there is no per-user store in this app. Logged as deferred. |

**Open / close behaviour**

- Clicking a rail button opens its panel. Clicking the *selected* button closes it.
- Only one panel is open at a time.
- **The panel PUSHES the canvas; it never overlays it** (at ≥1120px — see §2.7). The owner's
  complaint is that the canvas is crowded out; an overlay would hide nodes he is looking at, and a
  push keeps every node visible at a smaller zoom. The canvas is the main object on this screen.
- Default on first load of a run: **Overview open.** A run view that opens as a bare canvas does not
  say which run it is. Closing it is one click, and the last choice is remembered for the session
  (`sessionStorage`, one key for the whole app, not per run).
- Exception, and it overrides the remembered choice: see the Questions auto-open rule in §3.2.

**Transition:** width animates `160ms ease-out`; contents do not fade. Under
`prefers-reduced-motion: reduce`, the width change is instant.

### 2.7 Narrow widths

| Viewport width | Behaviour |
|---|---|
| ≥ 1120px | Rail 48 + panel 400 push; the canvas keeps ≥ 672px |
| 720px – 1119px | Rail stays 48 and stays visible. The panel becomes an **overlay**: `position: absolute; left: 48px; top: 0; bottom: 0`, 400px wide, `border-right: 1px solid --color-line`, `box-shadow: 24px 0 48px -32px rgba(0,0,0,0.9)` (the mirror of `sheet.tsx:136`). No scrim — the canvas behind stays readable and clickable. |
| < 720px | As above, but the panel is `calc(100vw - 48px)`. The rail still does not collapse. |

The switch is a media query, not a measurement: `@media (min-width: 1120px)`. 48 + 400 + 672 = 1120.

### 2.8 What the canvas must do

`orchestration-canvas.tsx` currently reserves `HUD_RESERVE = HUD_WIDTH + 28 = 428px` of left padding
whenever a HUD exists (`fitOptionsFor`, line 193). **With the rail, that reservation is wrong** —
the panel is now a layout sibling and has already been subtracted from the pane width. Change:

- The panel is not reserved for at all. It is outside the pane.
- The only thing still floating over the canvas is the notice stack (§4.3). Reserve for it, and only
  when one is rendered: `NOTICE_RESERVE = 360 + 28 = 388px` of left padding, else `0`.
- Re-run the fit when the pane width changes (panel opening or closing changes it by 400px). Without
  this the graph stays fitted to the old width and either overflows or sits in a corner.

## 3. The panels, and what they are called

### 3.1 The mapping

Seven tabs become **five panels plus one conditional**. Everything demoted is named, with where it
went.

| Today (`sheet.tsx:226-234`) | Becomes | Label | Accessible name / tooltip |
|---|---|---|---|
| `ticket` "Ticket" | **Overview** panel, section "What you asked for" | **Overview** | "Overview — what you asked for, what you gave it, and how this run went." |
| `env` "Run" | Overview, section "Machine and cost" | *(no rail entry)* | — |
| `agents` "Agents" | Overview, section "Who worked on it" | *(no rail entry)* | — |
| `chat` "Chat" | **Chat** panel | **Chat** | "Chat — send this run an instruction or a reference image. The panel says whether it is delivered live or queued." |
| `code` "Code" | **Files** panel | **Files** | "Files — the folders and files this run wrote, and what is in them." |
| `verdict` "Verdict" | **Result** panel | **Result** | "Result — whether it passed, what it was checked against, and where the work landed." |
| `trace` "Trace" | **Activity** panel | **Activity** | "Activity — every event this run sent, oldest first. The raw record." |
| *(new — plan dialogue + design lock)* | **Questions** panel | **Questions** | "Questions — what this run asked you, and your answers. Opens by itself when it is waiting on one." |

Every rail button carries both `aria-label` and `title` with the sentence above. An icon-only rail
with no text affordance is a guessing game; the tooltip is not optional polish.

### 3.2 Why each promotion and each burial

**Overview is promoted and is the default.** It is literally what the owner asked for — "an overview
of the project and what has been entered". Its four sections, in order:

1. *This run* — status pill, plain-English outcome sentence, elapsed, model, run id, and the
   **Cancel / Resume** buttons from `RunHud`. Actions live with the status they act on.
2. *What you asked for* — the ticket brief (`TicketAttachmentsPanel` order preserved: the short
   scannable list first, the unbounded brief second, per the reasoning at `sheet.tsx:700-728`).
3. *What you gave it* — attachments.
4. *Who worked on it* — `AgentRoster`, unchanged, still selecting canvas cards on click.
5. *Machine and cost* — `EnvironmentPanel` + `UsagePanel`.

**`env` is buried** because "the machine it ran on and what it cost" is a property of the run, and
Overview is the run. It was never a peer of Chat.

**`agents` is buried, and the reason it existed survives.** `sheet.tsx:886-901` documents a real job:
"the faster read when you already know the name", keyboard-reachable, click-to-select. All of that
is preserved inside Overview — the roster component is not modified, only re-parented. It is not a
rail entry because the canvas *is* the agent list, and an icon that opens a list of the things
already drawn on screen is the definition of a redundant rail entry.

**"Verdict" → "Result", not "Checks".** That panel carries `OutcomeNotice`, the artifact path, the
graded criteria and the adversary findings. "Checks" would be inaccurate about the artifact path, and
a friendly label that misleads is worse than the jargon it replaced.

**"Trace" → "Activity", not "Log" or "History".** It is the event stream with a live reconnect
control; "Activity" is the only plain word that covers both the record and the live tail.

**"Env" is gone as a word entirely.** So are "verdict" and "trace". Checked against the copy test at
`server/src/graph.test.ts:1026` — its banned list is `seat`, `digest`, `suite`, `freeze`, and none of
those appear in any label, eyebrow or tooltip in this spec. That test is not weakened or touched.

**Questions is conditional, and auto-opens. This is a hard requirement, not a suggestion.**

- The rail button renders when `planDialogue !== null` **or** the design lock is pending.
- When the run is stopped waiting on the owner (`run.status === "awaiting_input"` and the dialogue is
  answerable, i.e. the existing `planAnswerable` condition), the panel is **open on mount** and the
  rail button carries a `--color-warn` status dot. It overrides the remembered session panel.
- When the dialogue is closed/settled, the button stays (it is the record of what was asked) with no
  dot, and does not auto-open.

The reason is written into the source already and must not be re-litigated
(`app/runs/[runId]/page.tsx`, the swap comment): *"A Plan panel that covered a plan park would mean
clicking a card on the canvas costs the owner the only control that can un-stick his run."* Behind an
icon with no auto-open, that control is one click away from a reader who does not know it exists.

### 3.3 The draft-loss trap

`sheet.tsx:662-680` mounts the chat on every tab and merely hides it, because the composer's draft
text lives in `OrchestratorChat`'s own state and switching tabs would destroy it. **The rail
reintroduces this hazard in a worse form**: closing the panel unmounts it entirely.

Requirement: closing or switching away from the Chat panel must not lose typed text. Either lift the
draft to the run page's state and pass it down, or keep the Chat panel mounted and hidden while any
panel is open. Lifting is preferred — a hidden always-mounted panel is what the current file already
calls out as a cost.

## 5. Verification the implementer owes

This lane wrote no tests. These are the ones the build must come with, each named with the mutation
that has to turn it red. A spec asserting "the element exists" is the defect this repo is known for —
assert content and order.

1. **`rail.browser.spec.ts` — the rail exposes exactly these accessible names, in this order.**
   Assert the array `["Overview","Chat","Files","Result","Activity"]` read off the toolbar's buttons
   on a run with no dialogue. *Mutation: reorder two entries, or change one label string → red.*
   A test that only asserts `toBeVisible()` on the toolbar does not count.
2. **Clicking a rail button opens the named panel and its content.** Assert a string only that panel
   renders (e.g. Files → a path from the workspace tree; Result → the artifact path).
   *Mutation: point the Files button at the Result panel → red.*
3. **The panel pushes and the canvas re-fits.** Measure the canvas pane's width with the panel open
   and closed; assert it differs by the panel width and that no node's bounding box lands under the
   rail. *Mutation: change the panel from a flex sibling to `position: absolute` → red.*
4. **Questions auto-opens on an answerable park.** Fixture: `awaiting_input` + a dialogue with open
   questions. Assert the panel is open on first paint without a click, and the rail button carries
   the warn dot. *Mutation: remove the auto-open branch → red.* This is the one that protects the
   owner's un-stick control.
5. **The icons actually render.** Assert the computed `mask-image` of a rail icon is non-`none` and
   that the element's box is 24x24. *Mutation: delete one PNG from `public/rail/` → red.* Without
